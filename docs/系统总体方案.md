## 第一章 系统概述

### 1.1 系统定位与设计目标

本系统是一套基于飞书多维表格的**个人间隔重复学习与知识管理系统**，通过飞书群内文字指令实现学习卡片管理、答题记录、间隔重复算法推导、每日推送、知识检索、待办管理、洞察归档等核心功能，并与Obsidian知识库、AnythingLLM本地AI引擎、Hermes Agent调度框架深度融合。

**设计目标：**
- 零公式字段：所有计算通过Python脚本derive完成，表内无公式字段，避免平台限制
- 事件溯源：复习流水只追加不修改，derive从流水派生当前状态
- 幂等可靠：所有写操作有event_id唯一键，重复触发不产生重复数据
- 宁可慢不可假：数据真实性优先于速度，所有状态必须可追溯
- 本地优先：核心逻辑在本地Python脚本执行，不依赖云端服务可用性
- 三系统融合：飞书系统为核心，Obsidian为知识沉淀层，AnythingLLM为AI引擎层，Hermes为调度层

### 1.2 核心设计原则

| 原则 | 说明 | 实现方式 |
|---|---|---|
| 事件溯源 | 流水只追加，状态从流水派生 | 复习流水表append-only，derive脚本计算当前状态 |
| 零公式字段 | 表内无公式，全写入字段 | 学习卡字段全部为存储字段，无formula/lookup |
| 单一真源 | 流水是唯一真源，其他表为派生 | 学习卡状态=derive(流水)，可随时rebuild-all |
| 幂等 | 重复触发不产生重复数据 | event_id=message_id，三层幂等键（自然日+任务名/event_id） |
| 宁可慢不可假 | 数据真实性优先 | 所有状态可追溯到具体流水，禁止静默失败 |
| 防复发 | 历史故障有拦截机制 | 不变量断言+契约测试+告警去重+白名单fail-closed |
| 插件直连 | Obsidian数据同步用插件JS，不用Python桥接 | local-rest-api + 12个JS功能脚本 |
| 一进一出 | 新增调度必须淘汰旧调度，总数不增 | 8个核心任务，不新增 |

### 1.3 适用范围与使用者

**适用场景：**
- 个人知识学习与间隔重复复习
- 学习卡片管理与状态跟踪
- 每日学习推送与待办提醒
- 知识检索与问答（AnythingLLM RAG）
- 学习数据统计与复盘
- 待办任务全生命周期管理（创建/销项/提醒/归档）
- 洞察记录与Obsidian知识库双向同步
- 机电工程/工程管理领域知识沉淀与双链关联

**使用者：**
- 系统管理员（白名单账号，可执行管理员修正指令）
- 普通用户（群内成员，可答题/记录洞察/销项/知识检索/创建待办）

| 系统 | 角色 | 核心功能 | 数据流向 |

**关键数据流：**

### 2.4 事件溯源机制

**流水只追加：**
- 复习流水表为append-only，不修改已有记录
- 每条流水包含：event_id（唯一）、card_id、result（会/不会/模糊/INIT/REVOKE）、timestamp、source、card_version、revision、superseded、untrusted等15个字段

**derive派生：**
- 学习卡当前状态 = derive(全部流水)
- 可随时rebuild-all从流水重建全部状态
- derive执行前后流水记录数不变（不变量断言）

**同日改判与跨日宽限期：**
- 6小时内同一张卡的多次答题取末条，前条标superseded
- INIT状态不参与改判分组（防复发拦截）
- 跨日23:59与00:01在6h内视为同一天

## 第四章 核心机制

### 4.1 间隔重复算法

**五锚点M值：**
- M0=首次学习，M1=1天，M2=3天，M3=7天，M4=21天
- 答对→升级到下一锚点，答错→降级到上一锚点
- 模糊→保持当前锚点

**升级门槛：**
- NOT_STARTED→LEARNING：首次答题
- LEARNING→REVIEWING：连续答对2次
- REVIEWING→MASTERED：连续答对3次
- MASTERED→ARCHIVED：超过180天无反馈（自动归档）

**关联卡片间隔微调：**
- 同tag卡片答对时，其他同tag卡片间隔微调≤20%
- 微调结果可重放（rebuild-all三次一致）

### 4.2 卡片状态机

```
NOT_STARTED → LEARNING → REVIEWING → MASTERED → ARCHIVED
     ↓            ↓           ↓           ↓
   (删除)      (重置)      (降级)     (冷归档)
```

**边界规则：**
- ARCHIVED卡片答题→拒绝（不静默写入）
- MASTERED卡片答不会→降级到REVIEWING
- 依赖未满足→不出题

### 4.3 幂等机制

**三层幂等键：**
1. event_id = message_id（消息级唯一）
2. 自然日+任务名（推送任务级唯一）
3. card_id+自然日（学习卡级唯一）

**重复触发处理：**
- 同一message_id重复→不产生重复流水
- 同一推送任务重复→标记已推送，不重复发送
- 推送记录文件：.push_records.json（本地幂等保护）

### 4.4 同日改判与跨日宽限期

**6小时规则：**
- 同一张卡6小时内多次答题→取末条，前条标superseded
- INIT状态不参与改判分组（防复发：INIT错误supersede已拦截）
- 跨日23:59与00:01在6h内→视为同一天，取末条

### 4.5 撤回与编辑

**撤回：**
- !revoke（不带参数撤最近一条）/ !revoke <event_id>
- 生成REVOKE反向流水，原流水标superseded
- derive重新计算状态

**编辑：**
- 用户编辑已发送消息→revision+1（预留实现，待验证）

### 4.6 安全模式

- 消息内容hash校验→不匹配→untrusted标记
- untrusted流水不参与derive计算
- 管理员可手动标记为trusted

### 4.7 冷启动

- INIT Seed：系统首次运行时生成初始流水
- intro_offset：新卡片错峰引入，避免一次性全部出题
- 每日新卡片上限：3张（可配置）

### 4.8 待办全生命周期管理（V14新增）

**创建：**
- 指令：「待办：任务名称【P1】截止:2026-09-20 类别:学习」
- 支持解析：优先级（P0/P1/P2→高/中/低）、截止日期、类别
- 创建后状态=待办，写入任务表

**销项：**
- 指令：「完成 任务名称」（支持模糊匹配，多个匹配时列出供选择）
- 销项后状态=已完成，写入实际完成日期
- 三报中显示今日已完成事项

**提醒：**
- 每日03:00随维护任务运行，检查未来3天内到期任务
- 到期提醒消息发送到飞书群，包含任务名/截止日期/剩余天数
- 已完成/已归档/已取消任务不提醒

**归档：**
- 指令：「归档 任务名称」
- 仅已完成任务可归档（反证：未完成任务拒绝归档并提示先完成）
- 归档后状态=已归档，从日常待办列表隐藏，历史记录保留
- 归档时写入复盘备注（归档时间戳）

**三报合并：**
- 早报：今日待办 + 昨日已完成 + 即将到期
- 午报：今日待办 + 今日已完成 + 即将到期
- 晚报：今日已完成 + 今日未完成 + 明日及未来待办

### 6.5 调度任务"一进一出"原则（V14红线）

**原则定义：** 新增任何调度任务前，必须先淘汰一个现有任务，确保任务总数不增长。

**为什么需要：**
1. **故障点倍增**：每个任务都是一个潜在故障点，任务数翻倍=故障概率翻倍
2. **维护成本**：个人系统维护精力有限，8个任务是可维护上限
3. **重复触发**：任务越多越容易出现功能重叠（如原Heartbeat在Windows和Hermes各跑一套）
4. **资源竞争**：任务过多会抢占CPU/内存/网络，影响核心任务执行

**执行规则：**

| 规则 | 说明 | 违反后果 |
|------|------|---------|
| 新增必淘汰 | 新增任务前必须明确淘汰哪个旧任务 | 禁止新增 |
| 功能合并优先 | 新功能优先合并到现有任务，不新建 | 禁止新建 |
| 失效即清理 | 任务连续3次失败或30天未运行→立即清理 | 强制清理 |
| 总数上限 | Windows≤5 + Hermes≤4 = 总计≤9 | 超限即整改 |
| 变更留痕 | 每次任务变更记录在施工日志（新增/淘汰/合并原因） | 审计追溯 |

**当前任务清单（8个，符合上限）：**

| 侧 | 任务 | 功能 | 不可替代性 |
|----|------|------|-----------|
| Windows | V16_MorningReport | 早报推送 | 核心推送，不可替代 |
| Windows | V16_NoonReport | 午报推送 | 核心推送，不可替代 |
| Windows | V16_EveningReport | 晚报推送 | 核心推送，不可替代 |
| Windows | V16_LearningPoll | 消息轮询（每5分钟） | 核心交互，不可替代 |
| Windows | V16_DailyMaintenance | 日常维护（03:00） | 数据健康，不可替代 |
| Hermes | obsidian_sync | Obsidian→AnythingLLM同步 | 知识同步，不可替代 |

**新增任务审批流程：**
1. 说明新功能必要性（为什么不能合并到现有任务）

### 8.2.3 定时自动同步与增量同步优化

**定时自动同步（不新增调度任务，遵循一进一出原则）：**
- 方案：Obsidian 启动时自动同步（将「一键同步.md」设置为启动默认页面）
- 实现：设置 → 核心插件 → 页面 → 启动时打开特定页面 → 选择「一键同步」
- 优势：不新增调度任务（Windows/Hermes），不用 Python 桥接，在 Obsidian 内用 JS 执行
- 频率：用户每次打开 Obsidian 时自动执行（通常每天 1-2 次，足够个人使用）
- 手动同步：仍可使用「一键同步.md」手动触发全量同步

**增量同步优化（基于内容哈希比较）：**
- 问题：原同步为全量同步，每次都重新生成所有笔记并写入，即使内容未变化
- 方案：在 vault 根目录创建 `.sync_state.json`，记录每条记录的内容哈希
- 实现：
  1. 同步时，计算飞书每条记录的内容哈希（基于关键字段）
  2. 与 `.sync_state.json` 中的哈希比较
  3. 哈希未变化 → 跳过写入（unchanged）
  4. 哈希变化或新记录 → 生成笔记并写入（created/updated）
  5. 同步完成后，更新 `.sync_state.json`
- 效果：
  - 首次同步：全量写入（与原方案相同）
  - 后续同步：只写入有变化的记录（通常 0-5 条，大幅减少 IO）
  - 同步速度：从 15-30 秒提升到 3-10 秒（取决于变化量）
- 状态文件：`.sync_state.json`（含 last_sync_time + hashes 字典）

**2026-09-14 反向同步修复（正则表达式bug）：**

问题：
- 反向同步.md在Obsidian阅读模式下无任何输出
- 反向同步检测到0条变更，即使Obsidian frontmatter中状态已修改

根因：
- `parseFrontmatter`函数的正则表达式 `/^(\w+):\s*(.*)$/` 中，`\w+` 只匹配英文字母、数字和下划线
- **不能匹配中文字段名**（如"状态"、"优先级"、"截止日期"）
- 导致所有中文字段都解析失败，frontmatter解析结果为空对象
- 即使Obsidian中修改了frontmatter字段，反向同步也检测不到

修复：
1. 正则表达式从 `/^(\w+):\s*(.*)$/` 改为 `/^([^:]+):\s*(.*)$/`
2. `[^:]+` 匹配除冒号外的任意字符，支持中文字段名
3. 同时简化反向同步脚本，去掉防重复执行锁（避免缓存导致无输出）

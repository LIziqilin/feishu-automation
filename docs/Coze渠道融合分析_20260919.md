# Coze 发布渠道与现有系统融合分析（V46，2026-09-19）

## 一、现有系统定位（先校准，避免过度设计）

| 维度 | 现状 |
|---|---|
| 用户 | 个人（无外部 C 端用户） |
| 核心入口 | 飞书总控群（群机器人指令）+ AnythingLLM GUI |
| 核心数据 | 飞书多维表格（任务/洞察/学习卡）+ Obsidian 笔记 |
| 自动化 | GitHub Actions（三察推送）+ Windows 计划任务（每日维护链） |
| 告警 | 企业微信群机器人 Webhook + 飞书群 |
| LLM | deepseek-v4-flash（AnythingLLM）+ Coze Bot（finished Brain） |

**结论**：这是一个**个人效率/学习/运维系统**，不是 C 端产品。所有渠道决策以此为基准。

## 二、七渠道逐一评判

| 渠道 | 与现有系统融合度 | 建议 | 理由 |
|---|---|---|---|
| **Coze API** | ★★★★★ | ✅ **已启用（V45-16）** | 统一服务核心，群指令「智能：xxx」已接 |
| **飞书多维表格字段捷径** | ★★★★★ | ✅ **优先落地** | 批量 AI 处理+人工审核，最被低估的高价值渠道 |
| **企业微信群机器人** | ★★★★★ | ✅ **已启用** | 告警/日报，现有 wecom_push.py |
| **Chat SDK** | ★★★☆☆ | ⚠️ **第二阶段** | 可嵌入自有网页/AnythingLLM，但个人系统非必需 |
| **微信小程序** | ★☆☆☆☆ | ❌ **不启用** | 无 C 端用户，审核成本高，TTS/语音不支持 |
| **抖音小程序** | ★☆☆☆☆ | ❌ **不启用** | 无抖音业务，无外部获客需求 |
| **微信客服** | ★☆☆☆☆ | ❌ **不启用** | 无售前/售后业务，转人工规则复杂 |

## 三、第一阶段：立即可落地（核心闭环）

### 1. 飞书多维表格字段捷径（最高优先级）

**现有系统可迁移的批量任务**：
| 现有脚本 | 迁移为字段捷径后 | 价值 |
|---|---|---|
| weekly_learning_report.py | 「学习周报」捷径（输入：周次；输出：周报草稿） | 人工审核后发群 |
| wrong_book.py（错题解析） | 「错题解析」捷径（输入：原题/错因；输出：AI解析+复习建议） | 批量生成学习卡 |
| profile_evolve.py（画像演化） | 「画像分析」捷径（输入：行为记录；输出：画像标签建议） | 人工确认后写画像表 |
| health_monitor.py | 「健康诊断」捷径（输入：监控指标；输出：健康报告+修复建议） | 运维看板 |

**接入步骤**：
1. Coze 后台 → Bot 「finished Brain个人AI助理」→ 发布 → 飞书多维表格
2. 授权飞书账号 → 配置输入字段（文本/数字/日期）→ 输出格式匹配字段类型
3. 在多维表格对应表新建「字段捷径」类型字段 → 映射输入列 → 逐行/批量触发
4. **验收**：有测试日志、有实际写入、人工审核列确认

### 2. Coze API 统一业务协议（已有，标准化）

现有 `coze_gateway.py` 已通。建议统一请求/响应结构：
```python
# 请求
{"intent": "CREATE_TASK", "content": "明天评审方案", "source": "FEISHU_BOT"}
# 响应
{"success": true, "task_id": "T10023", "status": "CREATED", "next_action": "CONFIRM_TIME"}
```
后续微信小程序/Chat SDK 接入时直接复用。

### 3. 企业微信群机器人（已有）

现有 wecom_push.py 已验证。保持现状：
- 运维告警（备份失败/桥接离线/健康异常）
- 日报/三察推送（飞书群为主，企业微信为备）

## 四、第二阶段：按需启用

### Chat SDK（嵌入自有网页）
- **场景**：把 Coze Bot 嵌入自有 HTML 仪表盘（如个人驾驶舱网页版）
- **前提**：第一阶段稳定运行 2 周以上
- **价值**：在浏览器里直接对话 Coze，不打开 AnythingLLM

### 统一用户账户
- 个人系统不需要多用户隔离，但建议在 API 调用中固定 `user_id="feishu-v45-local"`，便于审计

## 五、明确不启用的渠道（及理由）

| 渠道 | 不启用理由 |
|---|---|
| 微信小程序 | 无 C 端用户；审核周期长；TTS/语音不支持；个人系统用不上 |
| 抖音小程序 | 无抖音获客需求；一个 Bot 只能绑一个小程序，机会成本高 |
| 微信客服 | 无售前售后业务；转人工规则复杂；与企业微信群机器人是两套账号体系 |
| 微信公众号 | 无内容运营需求 |

## 六、验收标准（每个渠道上线前）

| 验收项 | 测试方法 |
|---|---|
| 授权有效 | 断开授权→接口失效→重新授权→恢复 |
| 消息收发 | 普通/长文本/特殊字符 |
| 多轮会话 | 连续 3 轮上下文 |
| 工具调用 | 实际创建/更新/查询/删除测试资源 |
| 会话隔离 | user_id 不同则数据隔离 |
| 异常处理 | 超时/限流/空参数 |
| 审计日志 | 请求/响应/耗时落库 |

## 七、最终架构（融合后）

```
飞书总控群（群机器人）  ──┐
企业微信群机器人（告警）──┤
GitHub Actions（定时）  ──┼──→ 统一 API 网关 ──→ Coze Bot（决策/工具编排）
多维表格字段捷径（批量）──┤                        ↓
AnythingLLM GUI（深度问答）┘                   飞书多维表格（数据落库）
                                                  Obsidian（知识沉淀）
```

**核心原则**：Coze 做决策和工具编排，飞书多维表格做事实源，群机器人做入口，不重复建设业务逻辑。

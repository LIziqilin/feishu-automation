### 3.3 恢复演练规范（定期实测，禁止只备份不恢复）

**演练频率：** 每周至少1次（每周巡检时执行）

**演练要求：**

- 必须比对记录数（完全一致才算通过）

- 演练后必须清理影子表
- 演练记录必须写入维保日志

**演练失败处理：**
- 记录数不一致→排查备份完整性/恢复脚本
- 数据损坏→立即使用上一个备份重新演练

**禁止行为：**
- ❌ 只备份不恢复演练（备份可能损坏而不知）
- ❌ 直接恢复到生产表（可能覆盖当前数据）
- ❌ 演练后不清理影子表（占用空间/混淆）
- ❌ 演练失败不记录（无法追溯）

### 待办全生命周期维护（V14新增）

**待办状态流转：** 待办 → 进行中 → 已完成 → 已归档

**日常维护要点：**
1. 每日03:00维护任务自动检查未来3天到期任务，发送到期提醒
2. 已完成任务可通过「归档 任务名」归档，归档后从日常列表隐藏

4. 任务表状态字段存在历史重复选项（"已完成"/"完成"、"待办"/"待开始"），代码已兼容两者
5. 三报（早/午/晚）自动合并当日待办和已完成事项

**常见问题：**
| 问题 | 原因 | 处理 |
|---|---|---|
| 待办创建后不在列表中 | 截止日期不在未来7天范围内 | 用「任务」指令查看全部，或检查截止日期 |

### 4.2 各类告警处理手册

#### 4.2.1 权限失效告警

**现象：** 飞书API返回91403无权限/Token过期

**处理步骤：**
1. 确认lark-cli认证状态：`lark-cli auth status`
2. 如Token过期：重新认证`lark-cli auth login`
3. 如权限不足：检查应用权限范围，申请base:record:read/write
4. 验证：执行一次简单查询`lark-cli base +table-list --base-token XXX`
5. 记录：写入系统事件日志表（ALERT类型）

**防复发：** 凭据漂移检测（scripts/check_health_abnormal.py），定期检查凭据有效性

---

#### 4.2.2 解析失败告警

**现象：** 消息解析失败/指令不识别

**处理步骤：**
1. 查系统事件日志表INSTRUCTION类型，找到解析失败的消息
2. 确认消息内容是否符合指令格式
3. 如为合法指令但解析失败：排查parser逻辑
4. 如为非法指令：发送回执"❓ 没看懂，请发：会/不会/模糊"
5. 记录：解析失败计入日志，不崩溃

**防复发：** 解析失败有明确回执，不静默失败

---

#### 4.2.3 写入失败告警

**现象：** 流水写入失败/DLQ非空

**处理步骤：**
1. 查.dlq_queue.json，确认DLQ中有未处理消息
2. 手动触发DLQ重试：`python scripts/dlq_consumer.py`
3. 验证：流水表真实新增记录（非仅改状态）
4. 如重试失败：排查写入失败原因（权限/表结构/网络）
5. 记录：DLQ重试结果写入日志

**防复发：** DLQ非空告警+真实重试逻辑+幂等保障

---

#### 4.2.4 降级告警

**现象：** LLM降级（AnythingLLM不可用→DeepSeek→Coze→本地检索）

**处理步骤：**
1. 查llm_config.json确认当前启用的顺位
2. 如primary（AnythingLLM）不可用：检查AnythingLLM服务是否运行（http://localhost:3001）
3. 如secondary（DeepSeek）不可用：检查API密钥/网络/余额
4. 如tertiary（Coze）DEGRADED：正常（无密钥，预留实现）
5. 如fallback（本地检索）：正常兜底
6. 记录：降级事件写入日志

**防复发：** 四顺位降级链+每层可独立降级+末层兜底有明确回执

#### 4.2.5 熔断告警

**现象：** 连续失败达阈值→熔断→定期探测→恢复

**处理步骤：**
1. 确认熔断触发原因（连续失败次数/失败类型）
2. 等待探测周期（默认30秒）
3. 验证探测成功后自动恢复
4. 如持续熔断：排查根因（API不可用/网络故障/配置错误）
5. 记录：熔断/探测/恢复事件写入日志

**防复发：** 熔断四段完整（探测→回切→验证→回滚）

## 第五章 故障排查手册

### 5.1 排查方法论（五问根因+分层定位）

**五问根因法：**
```
故障现象 → 第一问：为什么发生？ → 第二问：为什么没被发现？
→ 第三问：为什么没被拦截？ → 第四问：为什么会复发？
→ 第五问：怎么防止再次发生？（防复发措施）
```

**分层定位：**
```
用户层（飞书群消息） → 应用层（learning_system.py解析/处理）
→ 集成层（v19_integration.py告警/看门狗/管理员）
→ 数据层（飞书多维表格读写） → 外部服务层（AnythingLLM/DeepSeek/Coze/GitHub）
```

**排查顺序：** 从用户层向下逐层定位，先确认哪一层出现异常，再深入该层排查

### 5.2 常见故障速查表

| 现象 | 可能原因 | 排查命令 | 处置 |
|---|---|---|---|
| 发消息无回执 | 轮询任务失效/消息未处理/lark-cli认证失败 | schtasks /query查V16_LearningPoll；查processed_messages.json；lark-cli auth status | 启用任务/手动触发轮询/重新认证 |

### 5.3 回滚 SOP

**回滚原则：**
- 变更前必须全量备份
- 回滚必须从备份恢复，不手动修改
- 回滚后必须验证系统正常

**三类回滚：**

#### 5.3.1 Seed回滚（学习卡初始数据）

**适用场景：** 学习卡数据损坏/INIT流水异常

**回滚步骤：**
1. 确认备份文件存在且可解析
2. 从备份恢复学习卡表到影子表（见3.2恢复SOP）
3. 比对记录数和关键字段
4. 如确认生产表损坏：用影子表覆盖生产表（需用户确认）
5. 执行rebuild-all从流水重建derive字段
6. 验证：答题闭环正常/状态机正常

#### 5.3.2 derive回滚（派生状态）

**适用场景：** derive结果异常/学习卡状态错误（流水正常）

**回滚步骤：**
1. 确认流水表正常（无丢失/无异常）
2. 执行rebuild-all从流水重建所有derive字段
3. 验证：rebuild三次结果一致
4. 如rebuild后仍异常：排查derive逻辑（可能是代码bug）

#### 5.3.3 解析器回滚（消息解析逻辑）

**适用场景：** 解析器升级后出现大量解析失败

**回滚步骤：**
1. 确认解析器备份存在（learning_system.py.bak_*）
2. 用备份覆盖当前解析器（需用户确认）
3. 验证：解析正常/回执正常
4. 记录：回滚原因+时间+验证结果
5. 后续：排查新版本解析器问题，修复后重新发布

**回滚后验证清单：**
- [ ] 轮询任务正常（发消息有回执）
- [ ] 答题闭环正常（流水新增+derive更新+回执）
- [ ] 推送正常（手动触发一次推送）
- [ ] 数据一致性（流水数+卡片状态与回滚前一致）
- [ ] 无新增告警

## 第六章 变更管理

### 6.1 变更流程（评估→备份→实施→验证→记录）

```
① 变更评估
   - 影响面分析（关联哪些功能/表/脚本）
   - 风险评估（低/中/高）
   - 回滚方案准备

② 全量备份
   - 执行backup_with_rotation.py
   - 确认备份文件可解析
   - 记录备份文件名+大小+记录数

③ 变更实施
   - 最小改动原则
   - 每步改动后立即验证（写后回读）
   - 不修改生产流水记录

④ 变更验证
   - 端到端四段（真实触发→数据落点→用户可感知→反向验证）
   - 反证验证（构造反例）
   - 三项回归（关联回归/三次重放/防复发验证）
   - 故障重演（重新注入原故障，确认被拦截）

⑤ 变更记录
   - 写入施工日志（日期/内容/改动文件/验证结果）
   - 更新相关文档（总体方案/维保资料/用户手册）
   - 五方会签（工程/质检/运维/学习/效率）
```

### 6.2 解析器发布规范（测试群24h→回归→生产）

**发布流程：**
```
① 开发完成
   - 新解析器代码完成
   - 单元测试通过

② 测试群验证（24小时）
   - 部署到测试群（非生产群）
   - 运行24小时，观察解析成功率/回执正确性
   - 收集异常案例

③ 回归测试
   - 执行全量回归（e2e+契约测试+数据基线）
   - 与基线比对，无新增失败项
   - rebuild-all三次一致性

④ 生产发布
   - 备份当前生产解析器（.bak_后缀）
   - 部署新解析器到生产
   - 观察1小时，确认无异常

⑤ 发布后验证
   - 每日巡检确认正常
   - 如出现异常：立即回滚（见5.3.3解析器回滚）
```

**配置变更范围：**

**禁止行为：**

## 第七章 维护成本控制

### 7.1 维护时间统计与阈值

**维护时间统计：**
- 每日巡检：5分钟×30天=2.5小时/月
- 每周巡检：15分钟×4周=1小时/月
- 每月巡检：30分钟×1月=0.5小时/月
- 故障处理：按需（目标≤1小时/月）
- 变更实施：按需（目标≤1小时/月）
- **合计目标：≤6小时/月**

**阈值告警：**
- 月维护时间>8小时→P2告警，排查自动化不足
- 周维护时间>3小时→P2告警，排查异常频发
- 单次故障处理>4小时→P1告警，排查根因复杂

**统计方法：**
- .maintenance_counter.json记录维护操作次数
- 维保日志记录每次维护耗时
- 每月巡检时统计上月维护总时长

### 7.2 自动化减负（一进一出原则）

**一进一出原则：**
- 新增一个自动化任务→必须移除一个旧任务或合并
- 新增一个调度→必须确认不与现有调度重复
- 目标：调度任务数不增加，维护成本不上升

**当前调度任务（V16系列，6个）：**
| 任务 | 触发 | 功能 | 可否合并 |
|---|---|---|---|
| V16_MorningReport | 07:30 | 早报 | 否（独立功能） |
| V16_NoonReport | 12:00 | 午报 | 否（独立时间） |
| V16_EveningReport | 21:00 | 晚报 | 否（独立时间） |
| V16_LearningPoll | 每10分钟 | 轮询 | 否（核心功能） |
| V16_DailyMaintenance | 03:00 | 维护（备份/清理/derive） | 可合并更多维护项 |
| Heartbeat-Morning/Noon | 07:30/12:00 | 心跳 | 可合并到Report任务 |

**自动化减负已实现：**
- 备份自动（V16_DailyMaintenance每日03:00）

# 企业微信替补备用系统 · 落地方案（V15 备份层）

> 版本：V15.1-backup　日期：2026-09-16
> 目标：在不重建系统、不重复存数据的前提下，让企业微信成为飞书系统的**替补/冗余通道**，飞书出问题时不丢通知、不中断关键流程。
> 原则：本地大脑永不下线；云端只做"数据真源 + 推送管道"，备用就是把这两件事做冗余、做可切换。

---

## 一、一句话结论

- **能立刻做、且已做一半**：企业微信群机器人 = 飞书群的**备用推送管道**。三报、健康告警现在已双发飞书+企微，飞书挂了企微仍能收到。
- **不能立刻做**：在企微里直接对系统下指令（新建任务/完成/查询），因为这需要**公网回调 URL**，本机是家用机、无公网。要用必须加内网穿透。
- **不建议做**：把数据搬到企业微信"智能表格"另建一套。现有数据真源、同步链路都长在飞书多维表上，迁过去等于推翻重来，反而增加风险。备用的正确做法是**飞书表定期本地备份 + 企微只读看板**，不是再造一个数据库。

---

## 二、系统模块 × 企业微信能力 可行性对照

| 飞书系统现有模块 | 它的作用 | 企微能否替代/冗余 | 前置条件 | 结论 |
|---|---|---|---|---|
| 总控群收指令（新建/完成/归档任务） | 人→系统的入口 | 群机器人 webhook **不能收**；自建应用可收但需公网回调 | 内网穿透 | ⏳ 需穿透，先保留飞书为主 |
| 三报（早/午/晚）推送 | 系统→人 | 群机器人 webhook **可推 markdown 看板** | 无（已通） | ✅ 已双发，可加强为看板 |
| 健康监控告警 | 异常兜底 | 群机器人 webhook **可推** | 无（已通） | ✅ 已双发 |
| 多维表格（任务/洞察/卡片/画像等 6 表） | 云端数据真源 | 企微智能表格 API 弱、不兼容现有同步 | — | ❌ 不迁移，改做本地备份 |
| 通讯录/身份 | @人、任务指派 | 自建应用可发应用消息 | 需 corpid+secret 换 token | 🟡 缺 corpid，待补 |
| Obsidian 笔记 / AnythingLLM / Ollama | 本地知识库与大脑 | 本就在本地，**不依赖飞书** | 无 | ✅ 天然离线可用 |
| GitHub Actions / Coze 工作流 | 定时任务、AI 节点 | 与企微无关，继续用 | 无 | ✅ 不受影响 |

**关键事实**：这套系统的"大脑"（Obsidian、AnythingLLM、Ollama 本地对话）全部在本机，本来就不连飞书也能用。飞书只承担两件事——**云端数据真源** 和 **推送管道**。所以"备用"只需把这两件事做冗余。

## 三、分层落地方案

### L0 —— 推送双发【已完成 ✅】
- 群机器人 webhook 已配（`wecom_secrets.env`），实测成功。
- `v15_features.send_chat()` 与 `health_monitor.py` 已加企微镜像：三报、告警**飞书+企微同时发**。
- 验收：飞书总控群与企微群同时收到消息；停掉飞书推送后企微仍到。

### L1 —— 企微只读看板（本周，无需公网）
目标：让企微群成为"**飞书出问题时也能一眼看到的状态面板**"。
1. **每日待办摘要看板**：每天早/午报时，除正文外，把「今日待办 N 条 / 逾期 N 条 / 近 24h 完成 N 条」用企微 markdown 推到企微群（飞书表照常读，企微只显示）。
2. **失败即升级**：任何脚本连续 3 次飞书推送失败 → 立即用群机器人 webhook 补推一条"飞书通道疑似故障"到企微群（现在是双发，再加"飞书失败计数→企微升级"逻辑）。
3. **数据定期本地快照**：把飞书 6 张表每天导出成 JSON 存到本地 `backup/feishu_snapshot/`，飞书整体不可用时，本地快照 + Obsidian 仍是完整副本。
- 前置：无（webhook 已通）。
- 验收：企微群每天收到摘要；手动停飞书推送能触发企微升级提醒。

### L2 —— 企微指令入口（需内网穿透后，1～2 周）
目标：复刻飞书群"发一句就建任务/销项"。
1. 用 frp / cpolar / 花生壳 把本机一个 HTTPS 端口暴露为公网回调 URL。
2. 在企微后台"小微助手"填回调 URL，用你提供的 **Token + EncodingAESKey** 做消息加解密。
3. 本地起一个轻量回调服务：收到企微消息 → 复用现有解析逻辑（新建/完成/归档）→ 写飞书表 → 回一句确认。
4. 主动消息：补 **企业 corpid** 后，用 Secret 换 access_token，可给指定人单发重要告警（不依赖群 webhook 失效时）。
- 前置：内网穿透（唯一硬阻塞）；补 corpid。
- 验收：在企微里发"新建任务：xxx"，飞书表出现记录并回确认。

### L3 —— 飞书整体不可用应急 SOP（文档化）
写一张"飞书宕机怎么办"卡片：
1. 看企微群是否还在收告警 → 在收说明本地脚本正常，只是飞书 API 挂。
2. 本地 `backup/feishu_snapshot/` 恢复最近数据；Obsidian 笔记继续作为工作副本。
3. 三报/告警临时只走企微群（webhook 不依赖飞书 API）。
4. 飞书恢复后，用现有「一键同步」把本地变更补回。

## 五、边界与不做项（避免走弯路）
- ❌ 不把数据迁到企微智能表格——不重建数据库。
- ❌ 不用个人微信 Hook（itchat/WeChatFerry）——封号风险。
- ❌ 不在无公网时硬做企微"收消息"——回调必须公网可达，做了也是假的。
- ✅ 群机器人只做推送/看板，不要求它收指令。
- ✅ 数据真源始终是飞书多维表，本地快照只作灾难恢复，不双写。

## 六、总体验收（备用能力达标线）
1. 飞书群、企微群双收三报与告警；

3. 本地有每日全量表快照，可在飞书全挂时恢复；

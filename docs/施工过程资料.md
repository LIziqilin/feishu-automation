## 第一章 施工纪律（规范层）

### 1.1 施工红线（禁止行为清单）

| 编号 | 红线 | 说明 | 违反后果 |
|---|---|---|---|
| R1 | 禁止在生产数据上直接调试 | 调试必须使用影子表或TEST_前缀数据 | 数据污染，回滚 |

| R5 | 禁止照抄历史报告的"已完成/已启用" | 每项功能落笔前必须真实验证 | 文档虚标，整份返工 |

| R8 | 禁止静默失败 | 任何异常必须有回执或告警 | 问题不可见 |
| R9 | 禁止无限重试 | API超时重试2次（300ms/1s，总≤1.5s） | 雪崩 |
| R10 | 禁止跨类型替代删除 | 删除目标必须唯一确认，不得删非目标资源 | 误删 |

### 1.2 变更管理流程（备份→实施→验证→记录）

```
① 评估变更影响面（关联回归清单）
② 全量备份（backup_with_rotation.py，7轮滚动）
③ 实施变更（最小改动原则）
④ 端到端四段验证（真实触发→数据落点→用户可感知→反向验证）
⑤ 反证验证（构造反例，确认不产生脏数据）
⑥ 三项回归（关联回归/三次重放/防复发验证）
⑦ 记录变更（施工日志+fix_log）
⑧ 五方会签（工程/质检/运维/学习/效率）
```

### 1.3 调试纪律

**调试环境要求：**
- 调试数据必须使用TEST_前缀或影子表（shadow_前缀）
- 调试后必须清理测试数据（cleanup_test_data.py）
- 禁止在生产群发送测试消息（使用测试群或TEST_前缀）

**调试手法：**
- 日志分析：alerts.log / write_errors.log / task_maintenance_debug.log
- 数据比对：流水表vs学习卡表derive结果一致性
- 影子表验证：从备份恢复到影子表，在影子表上验证

### 1.4 维修纪律（故障处理五问根因法）

```
故障现象 → 第一问：为什么发生？ → 第二问：为什么没被发现？
→ 第三问：为什么没被拦截？ → 第四问：为什么会复发？
→ 第五问：怎么防止再次发生？（防复发措施）
```

**维修记录要求：**
- 每个故障必须记录：现象/影响范围/根因五问/修复动作/验证证据/防复发措施
- 修复后必须故障重演验证（重新注入故障，确认防复发机制能拦截）
- 只加代码不做故障重演=未验证=不通过

### 1.5 证据规范

**每条证据必须包含：**
- 命令原文（可复现）
- 退出码（0=成功，非0=失败）
- 原始返回（不截断，不修改）
- 复现命令（他人可复现）

**证据分级：**
- L0：字段存在（不算通过）
- L1：函数自测（不算通过）
- L2：端到端四段（真实触发→数据落点→用户可感知→反向验证，才算通过）

### 1.6 验收纪律

**五方会签：**
| 角色 | 职责 | 否决权 |
|---|---|---|
| 工程 | 代码证据+实现正确性 | 有 |
| 质检 | 证据+反证+定级 | 有（主导） |
| 运维 | 副作用/日志/备份 | 有 |
| 学习 | 学习机制影响（间隔/升级/错因） | 有 |
| 效率 | 用户步数/摩擦/手机端 | 有 |

**REJECT强制返工锁：**
- 5/5通过→PASS→下一项
- 任一否决→本轮内立即返工→重新自检→报验→五方验收→会签
- 达到5/5前禁止输出下一项内容
- 3轮不过→BLOCKED（写明原因）→登记→下一项

### 3.1 调试案例集

#### 案例1：git.exe本地写入Permission denied

**现象：** git add/commit时报错Permission denied，无法写入.git/objects目录

**定位过程：**
1. 检查.git目录权限：发现.objects目录写入受限
2. 尝试git init重新初始化：失败
3. 检查是否有其他进程占用：无
4. 确认是Windows文件系统权限问题

**根因：** .git/objects目录ACL权限异常，git.exe无法写入新对象

**解决：** 改用dulwich（纯Python Git库）绕过git.exe权限问题
- dulwich版本：1.2.14
- 工具脚本：dulwich_commit_simple.py / dulwich_remove_tests.py
- 验证：9个提交全部成功推送到GitHub

**防复发：** 记录在《系统维保资料》故障排查手册，遇到git权限问题直接用dulwich

#### 案例2：自动化队列表查询失败

**现象：** lark-cli base +record-list查询tblN2nL4hP9Qz7fK返回"Expecting value: line 1 column 1 (char 0)"

**定位过程：**
1. 检查base_token和table_id：与config_local.py一致
2. 尝试查询其他表：正常
3. 检查lark-cli返回：空响应（非JSON）
4. 确认：表可能不存在或权限不足

**根因：** 自动化队列表tblN2nL4hP9Qz7fK可能不存在或已删除，或当前应用无该表权限

#### 案例3：Python -c内联脚本中文SyntaxError

**现象：** 频繁出现unterminated string literal/bytes中文SyntaxError

**定位过程：**
1. 检查Python版本：3.10（支持中文）
2. 检查编码：PowerShell默认编码问题

**根因：** PowerShell到python -c的编码传递问题，中文字符被截断

### 故障案例5：跨日不合并（原23:59与00:01被视为两天）

**故障现象：** mark_superseded_same_day只按自然日，23:59答题与次日00:01答题被视为两天，不合并，导致同日改判失效

5. 怎么防止再次发生？→ 6小时宽限期+effective_day计算+真实跨日验证

**修复动作：**

- 拦截：不误报（不产生stale告警）

### 8.2 遇到的问题与解决方案（按时间顺序）

#### 问题1：Templater模板文件夹配置错误

**现象**：执行`Templater: Insert template`时报错"Couldn't retrieve template files from templates folder .obsidian/scripts"

**根因**：Templater实际读取的配置文件是`plugins/templater-obsidian/data.json`（不是`.obsidian/templater-obsidian.json`），其中`templates_folder`被错误设置为`.obsidian/scripts`，`user_scripts_folder`为空。

**解决方案**：
1. 定位正确配置文件：`D:\AI\finished Brain\.obsidian\plugins\templater-obsidian\data.json`
2. 修改配置：`templates_folder: "Templates"`，`user_scripts_folder: ".obsidian/scripts"`
3. 重启Obsidian使配置生效

**验证**：重启后Templater可正常读取Templates文件夹中的8个模板。

#### 问题2：Templater"No active editor"错误

**现象**：选中模板后报错"No active editor, can't append templates"

**根因**：Templater的`Insert template`命令需要一个活动的编辑中的笔记，才能把模板内容插入进去。用户在没有打开任何笔记的情况下执行了命令。

**解决方案**：先打开一个笔记（或新建笔记），光标放在编辑区域，再执行Templater命令。

#### 问题3：动态import本地JS文件被安全策略阻止

**现象**：Templater模板中使用`import('/.obsidian/scripts/sync_tasks.js')`动态加载外部JS文件，报错"Not allowed to load local resource: file:///D:/AI/finished%20Brain/.obsidian/scripts/sync_tasks.js" + "Failed to fetch dynamically imported module"

**根因**：Obsidian/Electron的安全策略不允许从`file:///`协议动态加载ES模块。

**解决方案**：放弃Templater动态import方式，改用**自包含DataviewJS脚本**——把所有同步逻辑（飞书API调用+文件操作+结果显示）全部内联到一个`.md`文件的`dataviewjs`代码块中，不依赖任何外部JS文件。

**验证**：自包含脚本可正常执行，无外部依赖。

#### 问题4：CORS跨域限制

**现象**：自包含脚本中使用浏览器`fetch`调用飞书OpenAPI，报错"Access to fetch at 'https://open.feishu.cn/...' from origin 'app://obsidian.md' has been blocked by CORS policy"

**根因**：Obsidian渲染进程的origin是`app://obsidian.md`，飞书服务器没有返回`Access-Control-Allow-Origin`头，浏览器CORS策略阻止请求。

**解决方案**：使用Obsidian内置的`requestUrl` API（通过主进程发起网络请求，不受CORS限制）。获取方式优先级：
1. `require('obsidian').requestUrl`（首选）
2. `app.requestUrl`（备选）
3. `window.Obsidian.requestUrl`（备选）

**验证**：使用`requestUrl`后，飞书API调用正常，Token获取成功，任务表/洞察表读取成功。

#### 问题5：DataviewJS页面不停跳转/循环

**现象**：同步过程中，「同步执行.md」页面不停刷新跳转，控制台大量ENOENT错误。

**根因**：同步过程中创建了42个任务笔记，Dataview检测到文件变化后自动重新索引，触发DataviewJS代码块重新执行，形成循环。

**解决方案**：添加**防重复执行锁**（window全局变量），同步只执行一次。

**验证**：添加锁后，同步只执行一次，页面不再循环。

#### 问题6：更新文件时ENOENT删除错误

**现象**：同步过程中控制台报"ENOENT: no such file or directory, unlink '...待办任务/已完成/xxx.md'"

**根因**：更新文件时，先`adapter.remove(filePath)`再`adapter.write(filePath, content)`，但文件可能已被其他操作删除，导致remove失败。

**解决方案**：更新文件时直接`adapter.write(filePath, content)`覆盖写入，不先删除。

**验证**：修改后无ENOENT删除错误。

## 第十章 V14 优化：定时自动同步与增量同步

### 10.1 施工概述

**目标**：
- 定时自动同步：不新增调度任务（遵循一进一出），实现 Obsidian 启动时自动同步
- 增量同步优化：基于内容哈希比较，只同步有变化的记录，提升同步速度

**施工时间**：2026-09-14
**施工人员**：AI工程专家

### 10.2 定时自动同步方案选型

| 方案 | 优点 | 缺点 | 决策 |
|---|---|---|---|
| 新增 Windows 任务计划 | 定时精确 | 违反一进一出原则（新增调度） | ❌ 不采用 |
| 新增 Hermes 调度任务 | 与现有架构一致 | 违反一进一出原则，需 Python 桥接 | ❌ 不采用 |
| Obsidian 启动自动同步 | 不新增调度，不用 Python，JS 直连 | 依赖用户打开 Obsidian | ✅ 采用 |
| Obsidian 定时插件 | 定时精确 | 需安装新插件，可能不稳定 | ❌ 不采用 |

**最终方案**：将「启动同步.md」设置为 Obsidian 启动时默认打开的页面，用户每次打开 Obsidian 时自动执行同步。

**设置方法**：
1. 打开 Obsidian 设置（`Ctrl+,`）
2. 左侧 → 核心插件 → 页面
3. 找到「启动时打开特定页面」→ 开启
4. 选择「启动同步」笔记

### 10.3 增量同步优化实施

#### 10.3.1 原方案问题

原同步逻辑为全量同步：
1. 读取飞书全量记录
2. 对每条记录生成笔记
3. 检查 Obsidian 中是否存在
4. 存在则比较完整内容，未变化则跳过，变化则覆盖写入
5. 不存在则创建

问题：
- 每次同步都需要生成所有笔记（即使内容未变化）
- 比较完整内容效率较低
- 同步速度慢（15-30秒）

#### 10.3.2 增量同步方案

基于内容哈希比较的增量同步：
1. 在 vault 根目录创建 `.sync_state.json`，记录每条记录的内容哈希
2. 同步时，计算飞书每条记录的内容哈希（基于关键字段，非完整笔记）
3. 与 `.sync_state.json` 中的哈希比较
4. 哈希未变化 → 跳过（unchanged，不生成笔记，不写入）
5. 哈希变化或新记录 → 生成笔记并写入（created/updated）
6. 同步完成后，更新 `.sync_state.json`

#### 10.3.3 哈希计算策略

每条记录的哈希基于关键字段计算：
- **待办任务**：任务名称/状态/优先级/截止日期/开始日期/实际完成日期/科目/类别/对接人/复盘备注/完成质量评分
- **洞察笔记**：洞察标题/洞察日期/科目/类型/价值评分/行动状态/洞察内容/AI摘要/底层规律/行动项/关联学习卡片/关联任务
- **学习卡片**：卡片问题/标准答案/卡片状态/科目/知识点分类/掌握度M/记忆等级/间隔天数/下次复习日期/上次复习日期/复习次数/连续正确次数/错因/费曼打分/标签/应用场景/底层规律/实战留痕/version/关联任务/SOP关联/来源/last_result/前置依赖

使用简单字符串哈希函数（DJB2变体），计算速度快，碰撞率低。

#### 10.3.4 效果对比

| 指标 | 全量同步 | 增量同步（首次） | 增量同步（后续） |
|---|---|---|---|
| API 调用次数 | 3次（三类表） | 3次 | 3次 |
| 笔记生成次数 | 80次（全部） | 80次 | 变化记录数（通常0-5） |
| 文件写入次数 | 80次 | 80次 | 变化记录数 |
| 同步速度 | 15-30秒 | 15-30秒 | 3-10秒 |
| IO 开销 | 高 | 高 | 低 |

### 10.5 关键技术决策记录

| 决策 | 原因 | 结果 |
|---|---|---|
| 不新增调度任务 | 遵循一进一出原则，避免故障点倍增 | Obsidian 启动自动同步 |

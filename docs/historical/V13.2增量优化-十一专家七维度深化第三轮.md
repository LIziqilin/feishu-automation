### 0.2 为什么这一轮抓的是"三阶问题"

前两轮的问题发现路径是：

```
V13：  方案写得对 → 但第一周施工时会踩空（硬伤）
V13.1：施工图能拿去施工 → 但施工图自己的数字对不上、工期太乐观、主路径切换后有二阶问题（精度）
V13.2：施工图的数字对了、工期实了、二阶问题有对策 → 但按图施工到第三步时，对策本身会引入三阶问题（落地细节）
```

**三阶问题的共同特征**：它们不是"方案错了"，而是"方案的对策在极端场景下会失效"。例如：
- 回执三态（V13.1 对策）本身是对的，但**告警没有去重**时，一次权限失效会触发 1440 条告警（60s 轮询 × 24h），用户反而看不到真正重要的那条
- event_id=message_id（V13.1 对策）本身是对的，但**用户撤回消息**时，旧 message_id 的 RECEIVED 记录变成孤儿，流水表里多一条永远不会到 COMMITTED 的记录
- hash 自检（V13.1 对策）本身是对的，但**hash 不匹配时"拒绝处理"**等于系统直接变砖，用户答的题全部丢失 —— 这比"带错处理"更糟

**本轮的方法论**：对 V13.1 的每一条对策，问一个问题——"这个对策在什么极端场景下会反过来制造问题？"12 条新发现全部来自这个追问。

## 第一章 🔴 N19：告警风暴 —— 回执三态的告警必须有去重与聚合

### 1.1 问题陈述

V13.1 第三章 3.1 定义了回执三态与三类告警：

```
态1 有、态2 无（超过 2 个轮询周期） → 解析失败告警
态2 有、态3 无                     → 写入失败告警，进死信队列
某日态1 总数 = 0 且用户确有答题     → 权限/轮询失效告警（最高级）
```

**但没有定义告警的去重与聚合。** 推演一下实际运行场景：

```
场景：im:message 权限在凌晨 02:00 过期（自建应用 token 过期）
  → 02:00 起，每 60s 轮询一次，每次态1 总数 = 0
  → 按 V13.1 规则，每次轮询都触发一条"权限/轮询失效告警"
  → 到用户早上 08:00 看到手机时，群里已有 360 条告警
  → 360 条相同内容的消息把昨晚的晚报、今早的早报全部冲掉
  → 用户翻了 5 屏全是"⚠ 权限失效"，反而不知道第一条是什么时候发的、持续了多久
```

**更严重的是**：告警刷屏会导致用户对告警**脱敏**。等真正的新故障出现时（比如 derive 影子对账发现差异），用户已经习惯性忽略群消息了。

### 1.2 对策：告警三级去重 + 聚合摘要

```
告警规则修订（写入运维手册与告警模块）：

一级去重（同类型告警 1 小时内只发 1 条）：
  告警键 = 告警类型 + 自然日 + 小时
  同一键已存在 → 不重复发送，只在内部计数
  例："权限失效"在 02:00–02:59 之间只发 1 条，内部计数 60 次

二级聚合（每小时末发一条摘要）：
  过去 1 小时内的所有告警（含被去重的）汇总为 1 条消息：
    「⚠ 过去 1 小时告警汇总：权限失效 60 次 / 解析失败 3 次 / 写入失败 0 次」
  这条摘要替代了 63 条独立告警

三级升级（持续超过阈值则升级通道）：
  同一告警类型连续 3 小时未恢复 → 从"群消息"升级为"@所有人 + 短信/电话"（若有）
  权限失效连续 3h = 系统已经断供 3h，必须确保用户知道
```

**成本**：告警模块增加约 30 行代码（去重键 + 计数器 + 定时摘要），无新增表（计数器可放内存，重启后重置——可接受，因为重启本身就是一个需要关注的事件）。

**与 V13.1 第七章 7.2 的"告警两级通道"的关系**：V13.1 分了"即时通道"和"批处理通道"，本轮在"即时通道"内部再加一层去重。两者不冲突：即时通道的告警先过去重，再决定是立刻发还是等小时摘要。

### 1.3 告警消息模板（与 V13.1 第五章 5.3 的四类回执统一）

```
告警统一模板（复用 feishu_sdk.send_message）：

  🔴 [P0] 权限失效
  首次发现：02:00:15
  持续时间：2h 15min（仍在持续）
  影响范围：复习链路全部中断，用户答题无法写入
  建议操作：检查自建应用 im:message 权限状态；若已过期则重新发版
  本次周期内已重复：135 次（已去重）

  🟠 [P1] 解析失败
  最近一次原始消息：「会 一」
  建议操作：该错例已记入错例日志，正则更新后回归测试
```

**关键**：告警模板里必须有"首次发现时间"和"持续时间"——这两个字段是用户判断"这是新故障还是老故障没修"的唯一依据。V13.1 的告警规则里没有这两个字段。

## 第二章 🔴 N21 + N25：字段分类表 + 上下文切换成本

### 2.1 N21：学习卡 8 个新字段的分类表（公式字段 vs 写入字段）

V13.1 D1b 要求"建学习卡 8 个新字段"，但**没有定义这 8 个字段各自的类型**。这在飞书多维表格里是一个关键区分：

| 字段类型 | 谁来写 | 被 derive --rebuild-all 覆盖？ | 风险 |
|---|---|---|---|
| **公式字段** | 飞书自动计算 | ❌ 不覆盖（公式字段不可手动写入） | 公式引用的源字段被 derive 改了，公式结果自动变——可能与 derive 计算结果不一致 |
| **写入字段** | derive 脚本写入 | ✅ 覆盖（derive 全量重写） | 如果用户手工改了，下次 rebuild 会被覆盖——符合单一真源原则，没问题 |
| **只读字段** | 不写，仅展示 | — | 无 |

**必须在 D1b 建表前明确每个字段的类型**，否则会出现"derive 写了一个公式字段"的静默失败（飞书 API 写入公式字段不报错但不生效），或者"公式字段自动计算的结果与 derive 写入的结果不一致"的双真源。

**建议的 8 字段分类表**（基于 V13 定稿的派生字段定义）：

| # | 字段名 | 类型 | 写入方 | 说明 |
|---|---|---|---|---|
| 1 | 卡片状态 | **单选（写入字段）** | derive | NOT_STARTED / LEARNING / MASTERED / ARCHIVED |
| 2 | 上次复习日期 | **日期（写入字段）** | derive | 取最近一条非 INIT 流水的时间戳 |
| 3 | 连续正确次数 | **数字（写入字段）** | derive | 从流水重算 |
| 4 | 掌握度 M | **数字（写入字段）** | derive | 按 V13.1 第十二章 12.4 的五锚点公式计算 |
| 5 | 下次复习日期 | **公式字段** | 飞书自动 | `=IF(状态="MASTERED", "", 上次复习日期 + 间隔天数)` |
| 6 | 间隔天数 | **数字（写入字段）** | derive | 由间隔重复算法派生 |
| 7 | 累计复习次数 | **公式字段** | 飞书自动 | `=COUNTIF(复习流水表.卡片ID, 本卡ID) - 1`（减 INIT） |
| 8 | 最后结果 | **单选（写入字段）** | derive | 最近一条流水的结果（会/不会/模糊） |

**关键约束**：
1. **公式字段（#5 #7）derive 绝对不写**——写入会静默失败。derive 的 `--rebuild-all` 必须跳过这两个字段。
2. **写入字段（#1 #2 #3 #4 #6 #8）用户绝对不手工改**——改了会被下次 rebuild 覆盖。在字段权限设置中设为"仅管理员可编辑"。
3. **公式字段 #5 引用的"间隔天数"是写入字段**——derive 改了间隔天数，下次复习日期自动变，这是正确的级联行为。
4. **公式字段 #7 的 COUNTIF 会包含 INIT 流水**——必须减 1，或在公式中加条件 `结果<>"INIT"`。建议用后者，更稳健。

**这张表必须在 D1b 建表时贴在旁边**，建一个字段确认一个类型。成本：建表时多花 5 分钟，但避免了"建完表发现字段类型错了要删了重建"的返工（飞书多维表格删字段会丢数据，且公式字段不能改类型）。

### 2.2 N25：上下文切换成本系数

V13.1 第二章用三点估算算出 D1 预算 216.7min（D1a 86 + D1b 79 + D1c 52），拆三晚。**但这个估算假设三晚是连续工作的**——实际上每晚开始时需要：

```
每晚启动成本（实测估算）：
  ① 重新打开飞书控制台、找到昨天的表/应用：3 min
  ② 重读昨天的产出（权限结论、建表进度、Seed 写入状态）：3 min
  ③ 重新进入"施工心态"（从日常工作切换到系统搭建）：2–5 min
  合计：8–11 min / 晚
```

三晚合计：**24–33min**，占 D1 总预算的 11%–15%。V13.1 的三点估算没有计入这个。

**修订后的 D1 预算**：

| 时段 | 纯施工预算 | 切换成本 | 合计 |
|---|:---:|:---:|:---:|
| D1a | 86 min | 0（第一晚无切换） | 86 min |
| D1b | 79 min | 10 min | 89 min |
| D1c | 52 min | 10 min | 62 min |
| **合计** | **217 min** | **20 min** | **237 min = 4.0h** |

**对首周预算的影响**：V13.1 乙案首周 3.9h（D1a+D1b+D1c+D2+D3，挪走 D4/D5），加上切换成本 20min 后为 **4.2h**，**略微超出 4h 承诺**。

**对策（二选一）**：
- **甲**：承认首周 4.2h，把"4h 承诺"改为"4.5h 承诺"（诚实标注：切换成本是真实存在的，不是估算错误）
- **乙（推荐）**：D1b 和 D1c 合并为一晚（1.5h + 10min 切换 = 101min ≈ 1.7h），减少一次切换。D1 从三晚变回两晚：D1a（86min）+ D1bc（101min）= 187min = 3.1h。首周合计 3.1h + D2(40min) + D3(60min) = **4.1h**，仍略超但更接近。

> **推荐乙的理由**：D1b（建表）和 D1c（写 Seed + 定规则）本来就是"建表→立刻往表里写数据"的连续动作，中间隔一天反而要重新熟悉表结构。合并后减少一次切换，且 D1bc 的 1.7h 在"一晚可执行区间"内（V13.1 定义的可执行区间是 30–60min，但 1.7h 对"搭建系统"这种需要深度专注的工作是可接受的——它不像"每天复习"那样需要低摩擦）。

**写入运维手册的估算规范补充**：

```
三点估算补充条款（V13.2 新增）：
  凡拆分为 N 个时段执行的任务，总预算 = 纯施工预算 + (N-1) × 切换成本
  切换成本默认 10min/次（含重新打开环境 + 重读产出 + 心态切换）
  若两个时段是"建表→写数据"这类强连续动作，应优先合并，减少切换
```

## 第三章 🔴 N20：撤回/编辑消息的幂等漏洞与孤儿记录清理

### 3.1 问题陈述

V13.1 第三章 3.2 定义了 `event_id = message_id`，第九章 9.3 定义了三层幂等键。**但没有考虑飞书群消息的"撤回"和"编辑"操作。**

推演场景：

```
09:00 用户发「会 1」→ message_id = om_123
      → 轮询读到 → RECEIVED om_123
      → 解析成功 → PARSED om_123 (card=1, result=会)
      → 写入流水 → COMMITTED om_123, event_id=om_123

09:01 用户撤回「会 1」（飞书支持 24h 内撤回）
      → om_123 在群里消失了
      → 但流水表里已经有一条 event_id=om_123 的记录
      → 系统事件日志表里有 RECEIVED/PARSED/COMMITTED 三条 om_123 的记录

09:02 用户发「不会 1」→ message_id = om_456
      → 正常写入，event_id=om_456
      → 业务层"card_id+自然日取末次"：om_456 时间戳更晚，取"不会" ✅
```

**结果**：派生结果是对的（取了"不会"），但流水表里多了一条"会"的记录，系统事件日志表里多了三条 om_123 的孤儿记录。

**这不是小问题**：
1. **流水表的"累计复习次数"会多算一次**（公式字段 #7 COUNTIF 会把 om_123 也算进去）
2. **契约测试⑭"当日重复作答取末次"能覆盖这个场景吗？**——V13.1 的⑭只测了"用户发了两条不同的消息"，没测"第一条被撤回了"。撤回的消息在飞书 API 里有 `deleted` 标记，但 V13.1 的轮询读取没有处理这个标记。
3. **如果用户撤回后不重发**（比如发现自己打错了，不想答了），流水表里就留下一条"用户答了会"的虚假记录——而用户实际上是撤回了。这违反了"宁可慢不可假"原则。

### 3.2 对策：撤回检测 + 流水标记删除（不物理删除）

```
轮询读取时增加撤回检测：
  飞书 im:message 接口返回的消息有 `deleted` 字段（布尔值）
  或：用 message_id 批量查询消息详情，已撤回的消息返回 "message has been deleted"

  检测到已撤回的消息：
    ① 系统事件日志表：该 message_id 的 RECEIVED/PARSED 记录标记 `superseded=TRUE`
    ② 流水表：该 event_id 的记录不删除（事件溯源只追加原则），但增列 `superseded`
       标记为 TRUE，derive 重算时排除 superseded=TRUE 的记录
    ③ 若该消息已 COMMITTED 且用户未重发 → 触发一条"用户撤回了作答，该卡今日无有效作答"的提示
```

**编辑消息的处理**：飞书支持"编辑已发送消息"，编辑后 message_id 不变，但内容变了。

```
检测到消息被编辑（消息内容与首次读取时不同）：
  ① 不自动重新解析（避免"用户编辑了一条闲聊消息，系统误以为是新指令"）
  ② 标记原解析结果为 superseded
  ③ 若编辑后的内容仍符合指令格式 → 按新内容重新解析，生成新的 PARSED/COMMITTED
     （event_id 仍为同一个 message_id，但流水表增列 `revision` 字段区分版本）
  ④ 若编辑后的内容不符合指令格式 → 该消息视为撤回，按 3.2 的撤回流程处理
```

**成本**：
- 轮询读取增加 `deleted` 字段检查：5 行代码
- 流水表增列 `superseded`（布尔）和 `revision`（数字，默认 0）：D1b 建表时加，2 分钟
- derive 重算时排除 superseded=TRUE：3 行代码
- 契约测试新增 **⑰ 撤回/编辑消息处理**：撤回后 derive 排除该记录；编辑后按新内容解析

**与"事件溯源只追加"原则的一致性**：superseded 是**标记删除**，不是物理删除。流水表里仍有完整记录，只是 derive 不计算它。这符合事件溯源"只追加、不删除"的根本原则——撤回本身也是一个事件（`结果=REVOKED`，或用 superseded 标记），应该被记录。

**更简洁的替代方案**：不增列 superseded，而是在检测到撤回时**追加一条反向流水**：

```
event_id = {message_id}|REVOKE|{撤回时间戳}
卡片ID = 原卡片ID
结果 = REVOKE
时间戳 = 撤回时间
来源 = USER_REVOKE
```

derive 重算时，遇到 REVOKE 记录则将其对应的原始流水排除。**这个方案不需要增列**，完全在事件溯源框架内解决。推荐这个方案。

## 第四章 🟠 N23：跨日边界的业务层幂等规则

### 4.1 问题陈述

V13.1 第三章 3.3 定义了"同一自然日内，同一 card_id 取时间戳最后一条为准"。**但跨日场景未定义。**

推演场景：

```
第 1 天 23:59 用户答「会 2」→ 流水 event_A，card_id=2，日期=第1天
第 2 天 00:01 用户答「不会 2」→ 流水 event_B，card_id=2，日期=第2天

业务层幂等键 = card_id + 自然日：
  event_A 的键 = card_2 + 第1天
  event_B 的键 = card_2 + 第2天
  → 两条键不同，都被视为"合法作答"

derive 重算时：
  连续正确次数：event_A 是"会"，event_B 是"不会" → 连续正确中断 ✅
  上次复习日期：取 event_B（第2天）✅
  但"第 1 天的复习"算不算一次有效复习？
```

**问题**：用户在 23:59 答的"会"，2 分钟后改了"不会"。按"同一自然日取末次"，这是两天的两条独立记录——但用户的真实意图是"我改主意了"，不是"我两天分别答了两次"。

**更极端的场景**：

```
第 1 天 23:59 答「会 2」→ 连续正确次数 +1（现在是 2）
第 2 天 00:01 答「不会 2」→ 连续正确次数归零

结果：用户 2 分钟内从"连续正确 2 次"变成"连续正确 0 次"
但如果用户是在 00:01 才答第一次（不会），那连续正确本来就是 0
区别在于：23:59 那条"会"算不算数？
```

### 4.2 对策：定义"答题会话"边界

```
引入"答题会话"概念：
  同一次早报推送后的所有答题，视为同一个"会话"
  会话边界 = 两次早报推送之间
  （早报通常在每天固定时间推送，比如 08:00）

  同一会话内，同一 card_id 取时间戳最后一条（V13.1 已有规则，扩展适用范围）
  跨会话的答题，视为独立的复习事件

  23:59 答题 → 属于"今天的会话"
  00:01 答题 → 如果早报还没推送（08:00 才推），仍属于"今天的会话"（因为新的早报还没出）
              → 如果早报已经推送了（比如 00:30 推送了新的早报），则属于"明天的会话"
```

**简化实现**：不引入"会话"的显式概念，而是定义一个**"答题宽限期"**：

```
答题宽限期规则（V13.2 新增）：
  同一 card_id 的两条作答，若时间戳相差 < 6 小时，视为"同一次复习的修改"
  → derive 取时间戳较晚的一条，较早的一条标记为 superseded（或用 REVOKE 反向流水）

  若相差 ≥ 6 小时，视为"两次独立复习"
  → 两条都计入连续正确次数计算（按时间顺序）

  6 小时的依据：正常人的睡眠周期。23:59 答题、00:01 改答案，相差 2 分钟 < 6h，视为修改；
  23:59 答题、第二天 08:00 再答，相差 8h > 6h，视为两次独立复习。
```

**为什么用 6 小时而不是"自然日"**：
- 自然日边界（00:00）是人为的，用户的"一天"通常是"睡醒到睡觉"
- 6 小时 roughly 对应一次睡眠，跨了 6 小时大概率是"新的一天"
- 这个阈值可以在运维手册中调整，默认 6h

**契约测试新增 ⑱**：
- 23:59 答"会"、00:01 答"不会"（相差 2min）→ derive 取"不会"，"会"被 superseded
- 08:00 答"会"、20:00 答"不会"（相差 12h）→ 两条都计入，连续正确中断
- 08:00 答"会"、13:00 答"会"（相差 5h）→ 取 13:00 的"会"，08:00 的被 superseded（同一次复习重复确认）

## 第五章 🔴 N22：安全模式 —— hash 不匹配时系统不能直接变砖

### 5.1 问题陈述

V13.1 第十章 10.1 定义：

```
instruction_parser.py 同样写入 __version__ 与 __parser_hash__
所有调用方启动时校验，不匹配则告警并拒绝处理消息
（拒绝处理 > 带错处理：宁可当天不记录，也不要记错）
```

**这个策略在"hash 不匹配是因为副本漂移"时是对的**——拒绝处理比记错好。但在另一种场景下会变成灾难：

```
场景：用户正常使用系统 2 周，每天答题 3 张。
  某天，feishu_sdk.py 被自动同步工具（SyncTrayzor / 坚果云）覆盖了一个旧版本
  → __sdk_hash__ 变了
  → 调用方启动时校验不匹配
  → 拒绝处理消息
  → 用户当天答的 3 张题全部丢失
  → 用户不知道系统拒绝了（拒绝时有没有回执？V13.1 没说）
  → 第二天用户继续答，继续丢失
  → 直到用户某天打开日志发现"最近 5 天全是 RECEIVED 但没有 COMMITTED"
```

**"宁可当天不记录，也不要记错"的前提是用户知道"今天没记录"。** 如果用户不知道，那"不记录"和"记错"在后果上是一样的——用户都以为自己复习了。

### 5.2 对策：三档安全模式（✅ 已裁决：选 B 档·降级模式）

```
hash 校验不匹配时，按以下三档处理（由用户在配置中选择，默认 B 档）：

A 档：严格模式（V13.1 原策略）
  不匹配 → 拒绝处理所有消息 → 群内发一条"⚠ 系统进入安全模式，今日答题暂不记录，请手动记录"
  适用：对数据准确性要求极高，能接受偶尔断供
  风险：用户没看到那条告警 → 静默丢数据

B 档（推荐 · 默认）：降级模式
  不匹配 → 仍处理消息，但写入流水时标记 `untrusted=TRUE`
  → derive 重算时，untrusted=TRUE 的记录**只用于展示，不用于计算掌握度/间隔**
  → 群内发一条"⚠ sdk/parser 版本不匹配，今日答题已记录但标记为不可信，建议尽快修复"
  → 修复后，用户可选择"将 untrusted 记录转为可信"（逐条确认或全量确认）
  适用：大多数场景，宁可数据带标记也不要丢数据
  优势：不丢数据，用户有知情权，修复后可恢复

C 档：宽松模式
  不匹配 → 仅告警，不影响处理（与 V13 之前的行为一致）
  适用：hash 校验还在调试期，或用户信任自己的同步工具不会出问题
  风险：副本漂移导致的错误数据可能被静默写入
```

**B 档的实现细节**：
- 流水表增列 `untrusted`（布尔，默认 FALSE）：D1b 建表时加，1 分钟
- derive 重算时：`untrusted=TRUE` 的记录计入"累计复习次数"（因为用户确实复习了），但**不计入连续正确次数和掌握度 M**（因为数据来源不可信）
- 修复后转为可信：提供一个脚本 `trust_records.py --from-date 2026-09-10 --to-date 2026-09-15`，将指定日期范围内的 untrusted 记录转为可信，并触发一次 derive 重算
- 告警消息必须包含"如何修复"的指引："请检查 feishu_sdk.py 的 __sdk_hash__，确认所有副本一致后重启服务"

**为什么推荐 B 档**：
1. **不丢数据**：用户答的题都记录了，只是标记为不可信
2. **不污染计算**：掌握度和间隔不受不可信数据影响
3. **可恢复**：修复后可以转为可信，不需要用户重新答题
4. **符合"宁可慢不可假"**：不可信数据不用于计算，等于"慢"（等修复后再算），但没有"假"（没有用错误数据计算）

**待拍板①**：A / B / C 三档选哪个？推荐 B。若选 A，则 V13.1 原策略不变，只需补一条"拒绝时必须发群告警"；若选 C，则 hash 校验退化为"仅告警"。

## 第六章 🟠 N24：三类回滚 SOP

### 6.1 问题陈述

V13.1 第二章 2.5 说"建表类失败可删表重来"，但**没有给具体的回滚步骤**。实际施工中，回滚的时间窗口很短（发现故障后要立刻回滚，否则数据污染扩大），没有 SOP 就会临场慌乱。

**三类最可能需要回滚的故障**：

| 故障 | 发生时机 | 污染范围 | 回滚难度 |
|---|---|---|---|
| **Seed 写入失败/写错** | D1c | 23 条 INIT 流水 | 低（只涉及流水表，且 INIT 不影响派生值） |
| **derive 上线后发现 bug** | D3 之后 | 学习卡表的 6 个写入字段全部可能被错误重算 | 中（需要从流水重算，但流水是正确的） |
| **解析器正则改错了** | D3 之后 | 新写入的流水可能被错误解析（比如"不会 2"被解析成"会 2"） | 高（错误的流水已经写入，需要识别并修正） |

### 6.2 Seed 回滚 SOP（D1c）

```
触发条件：seed_migration.py --execute 后发现写入的 23 条 INIT 有错误
  （比如 card_id 写错了、时间戳不对、来源字段没填）

回滚步骤：
  1. 立即停止所有后续施工（不要继续 D2/D3）
  2. 流水表中删除 来源=SEED_MIGRATION 的所有记录（23 条）
     → 因为 INIT 不影响派生值，删除是安全的（此时 derive 还没跑，学习卡表还是空的）
  3. 检查 seed_manifest.json，找出错误原因
  4. 修正 seed_migration.py
  5. 重新 --dry-run → 确认 manifest 正确 → --execute
  6. 验证：流水表 23 条 INIT，来源=SEED_MIGRATION，card_id 与学习卡表一一对应

回滚时间：5–10 min
不可回滚的情况：如果已经跑了 derive 并基于 INIT 做了其他操作（比如手动改了卡片状态），
  则需要先回滚 derive（见 6.3），再回滚 Seed。
```

### 6.3 derive 回滚 SOP（D3 之后）

```
触发条件：derive 上线后发现派生值错误（比如连续正确次数算错了、M 值异常）

回滚步骤：
  1. 立即停用 derive 的即时触发和 09:07 兜底（防止继续污染）
  2. 学习卡表的 6 个写入字段恢复为"上一次正确状态"
     → 方案 A（推荐）：从备份恢复。V13.1 第十章 10.3 定义了原子备份，
       用最近一次备份的学习卡表数据覆盖当前表
     → 方案 B：从流水重算。修正 derive 的 bug 后，直接 --rebuild-all，
       用正确的逻辑从流水重新计算（流水是只追加的，不会被 derive 污染）
  3. 验证：抽查 5 张卡的派生值，与手工计算结果一致
  4. 重新启用 derive 即时触发和 09:07 兜底

回滚时间：方案 A 5min（从备份恢复）；方案 B 10min（修正 bug + rebuild）
关键：derive 的回滚永远不需要改流水表——流水是单一真源，derive 只是从流水派生。
  只要流水是正确的，derive 随时可以 rebuild。
```

### 6.4 解析器回滚 SOP（D3 之后）

```
触发条件：解析器正则改错了，导致新写入的流水被错误解析
  （比如"不会 2"被解析成 card_id=2, result=会；或者"会1 不2 会3"只解析了第一条）

回滚步骤（最复杂，因为错误数据已经写入流水）：
  1. 立即停用解析器（防止继续写入错误流水）
  2. 识别错误流水：
     → 从系统事件日志表中，找出解析器版本变更后的所有 PARSED 记录
     → 与原始消息文本比对，找出解析结果与原始消息不符的记录
  3. 对每条错误流水：
     → 追加一条 REVOKE 反向流水（同第三章 3.2 的方案），标记原流水为 superseded
     → 用修正后的解析器重新解析原始消息，写入正确的流水
  4. 修正解析器正则，用 10.2 的容错边界表做回归测试
  5. derive --rebuild-all（从修正后的流水重新计算派生值）
  6. 验证：抽查错误时间段内的所有卡片，派生值正确

回滚时间：30–60min（取决于错误流水的数量）
预防：解析器的每次正则变更必须先在"测试群"跑 24h，确认无误后再切到生产群。
  这是 V13.1 没有定义的发布流程，本轮补上。
```

### 6.5 回滚 SOP 的落地要求

```
1. 三类 SOP 写入《运维手册》的"故障回滚"章节
2. D1c 施工前，Seed 回滚 SOP 必须贴在旁边（打印或打开在屏幕上）
3. D3 施工前，derive 和解析器回滚 SOP 必须贴在旁边
4. 每类回滚 SOP 的第一步都是"停止后续操作"——防止污染扩大
5. 回滚完成后，必须在系统事件日志表中记录一条 ALERT：
   「回滚事件：类型=derive，原因=连续正确次数计算错误，影响范围=5张卡，回滚耗时=8min」
```

## 第七章 🟠 N26：错因标记后的卡片状态机（待拍板②）

### 7.1 问题陈述

V13.1 第十二章 12.3 定义了错因标记（可选），四类错因：记不清 / 理解错 / 题目歧义 / 已过期。并说"理解错触发卡片需重写待办"。**但没有定义重写后的状态迁移。**

推演场景：

```
第 1 天：用户学了卡片 X（问："飞书自动化次数怎么算？"，答："按动作计，1流程2动作=2次"）
  → 答"会"，M=0.35，间隔=2天

第 3 天：复习卡片 X，答"不会 理解错"
  → 错因=理解错，触发"卡片需重写"待办
  → 连续正确次数归零，M 下降，间隔缩短

第 5 天：用户重写了卡片 X（新问："飞书多维表格自动化运行次数的计量口径是什么？"，
  新答："按流程计还是按动作计需实测确认，1流程含2动作时可能计1次或2次"）
  → 卡片内容变了

问题：
  ① 重写后，之前的复习流水（第1天"会"、第3天"不会"）还算数吗？
  ② M 值怎么算？从 0 开始还是保留之前的？
  ③ 间隔从哪天重新算？
  ④ 连续正确次数归零吗？
```

**如果保留旧流水**：第 1 天的"会"是针对旧卡片内容的，新卡片内容完全不同，那条"会"没有意义。但如果直接清零，又丢失了"用户曾经学过这个知识点"的历史信息。

### 7.2 对策：卡片版本化 + 状态迁移规则（待拍板②）

```
引入卡片版本号：
  学习卡表增列 `version`（数字，默认 1）
  流水表增列 `card_version`（数字，记录作答时的卡片版本）

  重写卡片 = version + 1，同时保留旧版本的内容（不删除旧卡片，而是"归档旧版本 + 创建新版本"）
  → 旧版本的卡片状态变为 ARCHIVED，不再进队列
  → 新版本的卡片状态为 NOT_STARTED，按新卡处理
  → 旧版本的流水全部保留，但 derive 重算时只计算当前版本的流水
```

**状态迁移规则**：

| 错因 | 重写后状态 | 旧流水处理 | M 值 | 间隔 | 连续正确 |
|---|---|---|---|---|---|
| 记不清 | 不重写，继续复习 | 保留 | 下降 | 缩短 | 归零 |
| **理解错** | **version+1，新版本 NOT_STARTED** | **旧版本流水保留但不计入新版本** | **新版本从 0 开始** | **重新计算（按新卡）** | **归零** |
| 题目歧义 | version+1（只改题面，答案不变） | 旧流水保留，**可选择迁移到新版本**（因为知识点没变） | 可保留旧 M（可选） | 可保留旧间隔（可选） | 可保留（可选） |
| 已过期 | 卡片状态变为 ARCHIVED，不重写 | 保留 | — | — | — |

**"理解错"和"题目歧义"的区别**：
- 理解错 = 用户对知识点的理解错了，卡片内容本身可能是对的，但用户需要重新学。**这种情况应该保留旧卡片，让用户重新复习**（不需要重写卡片，只需要缩短间隔）。等等——V13.1 说"理解错触发卡片需重写"，但我认为"理解错"不一定需要重写卡片，可能只是用户没理解。让我重新想一下。

实际上，V13.1 的四类错因对应的处置应该是：

| 错因 | 含义 | 处置 |
|---|---|---|
| 记不清 | 用户学过但忘了 | 缩短间隔，增加提取练习（不改卡片） |
| 理解错 | 用户对知识点的理解有误 | **需要重写卡片**（把用户误解的点写进答案，或拆成更细的卡片） |
| 题目歧义 | 卡片的题目写得不清楚，导致用户误解 | **需要改题面**（只改问题，不改答案） |
| 已过期 | 卡片内容已经过时（比如飞书 API 变了） | 归档或更新内容 |

所以"理解错"确实需要重写卡片——因为用户的误解说明卡片没有把知识点讲清楚，需要改写答案或拆分卡片。重写后，旧卡片的内容已经被替代了，旧流水针对的是旧卡片内容，**不应该计入新卡片的掌握度**。

**"题目歧义"只改题面不改答案**，知识点没变，所以旧流水可以迁移到新版本。

### 7.3 待拍板②（✅ 已裁决：选甲案·旧版本流水完全不计入新版本）

```
方案甲（推荐）：旧版本流水完全不计入新版本
  → 新版本从 0 开始，按新卡处理
  → 优点：干净，不会被旧的错误理解污染
  → 缺点：丢失了"用户曾经接触过这个知识点"的信息，新版本可能被推得太频繁

方案乙：旧版本流水计入新版本，但 M 值乘以衰减系数 0.5
  → 新版本的初始 M = 旧版本 M × 0.5
  → 优点：保留了"用户学过"的信息，新版本不会被当成完全陌生的卡
  → 缺点：衰减系数 0.5 是拍脑袋的，没有依据；且旧的"理解错"记录可能拉低 M

方案丙：旧版本流水只用于"累计复习次数"展示，不用于 M 和间隔计算
  → 用户能看到"这张卡你之前学过 3 次"，但计算从 0 开始
  → 折中方案
```

**推荐甲**：简单、干净、符合"重写 = 重新学"的直觉。乙的衰减系数没有学习科学依据，丙的实现复杂度高于甲但收益不明显。

**若采纳甲**，需要在使用手册中写明：
> 当你标记"理解错"并重写卡片后，该卡片将按新卡重新开始学习周期。之前的复习记录不会被删除，但不再影响新卡片的复习间隔。这是正常的——你已经用更好的方式重新学习了这个知识点。

## 第八章 🟠 N27：TCO（总拥有成本）核算模板

### 8.1 问题陈述

V13.1 第十三章 13.2 把 ROI 改为"掌握效率 = 新掌握卡数 / 维护小时数"。**但这只算了时间成本，没算金钱成本。**

这套系统的真实成本包括：

| 成本项 | 金额（估算） | 频率 | 备注 |
|---|---|---|---|
| 飞书基础版 | 0 元 / 月 | 月 | 个人版免费；若用专业版则 50 元/人/月 |
| DeepSeek API | 约 5–20 元 / 月 | 月 | 取决于调用量；V13.1 定义了告警线 |
| Coze | 0 元 / 月 | 月 | 个人版免费；若用付费版则另计 |
| 本地电费 | 约 5–10 元 / 月 | 月 | ThinkPad T480 待机功耗约 10W，24h 开机约 0.24 度/天 |
| 维护时间 | 约 2h / 周（迁移期）/ 0.5h / 周（稳态） | 周 | V13.1 定义了双窗口 30min/周 |
| 搭建时间（一次性） | 约 6–8h（V13.2 修订后） | 一次性 | D1a+D1bc+D2+D3+D4+D5 |

**如果不算 TCO，就无法回答"每掌握一张卡花了多少钱"这个关键问题。** 比如：
- 每月花 20 元 API 费 + 5 元电费 + 2h 维护时间，掌握 10 张卡
- 每张卡的成本 = 25 元 + 12min 维护时间
- 如果用户自己看书学，每掌握一个知识点可能花 30min + 0 元
- **哪个更高效？** 不算 TCO 就没法比。

### 8.2 TCO 模板（写入周报）

```
周报固定增列（V13.2 新增，在 V13.1 的"掌握效率"旁边）：

  本周金钱成本：
    DeepSeek API 消耗：X.XX 元
    飞书套餐摊销：X.XX 元（若付费）
    本地电费估算：X.XX 元
    合计：X.XX 元

  本周时间成本：
    维护投入：X min（来自 V13.1 的"本周维护投入"）
    复习投入：X min（新增：用户实际答题时间，可从流水表的时间戳差值估算）

  本周产出：
    新掌握卡数：X 张（跨过升级门槛）
    复习总次数：X 次

  单位成本：
    每掌握一张卡的金钱成本：X.XX 元/张
    每掌握一张卡的时间成本：X min/张（维护 + 复习）
    掌握效率：X 张/维护小时（V13.1 已有）
```

**实现方式**：
- DeepSeek API 消耗：从 DeepSeek 控制台导出，或在调用时记录到系统事件日志表（log_type=ALERT 或新增 log_type=COST）
- 电费：固定估算值（ThinkPad T480 24h 开机约 0.24 度/天 × 0.6 元/度 = 0.14 元/天 = 4.3 元/月），写入配置
- 复习投入：从流水表的 RECEIVED 到 COMMITTED 的时间戳差值估算（每条流水的处理时长），求和
- 单位成本：脚本自动计算，写入周报

**成本控制阈值**（写入运维手册）：

```
月度金钱成本 > 50 元 → 黄色告警：检查 DeepSeek 调用量，考虑降级到 ALLM 本地 RAG
月度金钱成本 > 100 元 → 橙色告警：强制降级，L5 只走 ALLM + 规则直答
周维护时间 > 2h（稳态期）→ 黄色告警：维护时间超标，检查是否有自动化可以补上
```

**TCO 的意义**：它不是为了"省钱"，而是为了**让用户知道这套系统的真实代价**。如果用户发现"每掌握一张卡花 5 元 + 20min"，而自己看书只花"0 元 + 30min"，那用户可以理性判断是否继续使用。**透明的成本比隐藏的成本更可持续。**

## 第九章 🟡 N28：系统事件日志表的分区 TTL

### 9.1 问题陈述

V13.1 第十三章 13.3 把四类日志（RETRIEVAL / INSTRUCTION / ALERT / DEGRADE）合并到一张"系统事件日志表"。**但没有定义各类日志的保留期限（TTL）。**

四类日志的价值衰减速度完全不同：

| 日志类型 | 内容示例 | 长期价值 | 建议 TTL |
|---|---|---|---|
| **RETRIEVAL** | 用户问了什么、命中几条、最终由第几顺位回答 | **高**（池化校准需要 90 天数据；知识盲区分析需要长期数据） | **90 天** |
| **INSTRUCTION** | 用户答了什么、解析结果、写入状态 | **中**（错例分析需要 30 天；超过 30 天的旧错例参考价值低） | **30 天** |
| **ALERT** | 告警记录、回滚事件 | **低**（告警的价值在于"当时看到"，历史告警只用于趋势分析） | **14 天** |
| **DEGRADE** | L5 顺位切换记录 | **中**（降级频率分析需要 30 天；用于判断"哪个顺位最常被用到"） | **30 天** |

**如果共用一个 TTL（比如 90 天）**：ALERT 日志会占用 6.4 倍的存储空间（90/14），且查询时大量旧告警干扰分析。
**如果共用一个 TTL（比如 14 天）**：RETRIEVAL 日志只有 14 天，池化校准（第 30 天）时数据不足，V13.1 的"hit_count=0 识别知识盲区"就无法实现。

### 9.2 对策：按 log_type 分区 TTL

```
系统事件日志表的 TTL 策略（V13.2 新增）：

  按 log_type 分区，各类型独立 TTL：
    RETRIEVAL  : 90 天
    INSTRUCTION: 30 天
    ALERT      : 14 天
    DEGRADE    : 30 天

  实现方式（飞书多维表格不支持行级 TTL，需脚本实现）：
    每日 03:00（低峰期）运行 log_ttl_cleanup.py：
      ① 查询各 log_type 中 时间戳 < (NOW - TTL) 的记录
      ② 删除这些记录（或归档到冷存储）
      ③ 记录删除数量到 ALERT 日志（log_type=ALERT, 内容="TTL清理：删除 RETRIEVAL 5 条"）

  冷存储选项（可选，P2）：
    删除前导出为 CSV，存到本地 archive/ 目录
    → 本地存储几乎无限，且不占飞书表格行数
    → 需要时可重新导入
```

**飞书多维表格的行数限制**：基础版多维表格有行数上限（通常 5 万行/表）。系统事件日志表如果不清理，按每天 100 条（3 张卡 × 3 态 + 检索 + 告警）计算，500 天就会满。**TTL 不是可选优化，是必须项。**

**TTL 清理脚本的配套**：
- `log_ttl_cleanup.py --dry-run`：输出将删除的记录数，不执行
- `--archive`：删除前导出 CSV 到本地
- 契约测试新增 ⑲：TTL 清理脚本只删除超过 TTL 的记录，不删除未过期的

**与 V13.1 的"原子备份覆盖两张只追加表"的关系**：系统事件日志表是第三张只追加表（V13.1 只说了流水表和检索日志表，V13.1 把检索日志表扩展为系统事件日志表后，备份范围应自动覆盖）。TTL 清理前的最后一次备份就是"归档"——如果备份策略是每日备份，那被 TTL 清理的记录已经在备份里了，不需要额外的冷存储。

## 第十章 🟡 N29：学习倦怠检测三指标

### 10.1 问题陈述

V13 和 V13.1 关注的都是"系统侧稳定性"——系统会不会断供、数据会不会丢、派生值会不会错。**但完全没有关注"用户侧稳定性"——用户会不会放弃使用。**

间隔重复系统的最大风险不是"系统坏了"，而是"用户不用了"。历史上很多 Anki 用户在 2–4 周后放弃，原因是"复习积压越来越多，每天打开都是 50 张卡，产生焦虑"。

V13.1 的新卡上限（1 张/日）已经在一定程度上缓解了积压问题，但**没有主动检测用户的倦怠信号**。

### 10.2 对策：三个倦怠指标 + 两级干预

```
倦怠检测指标（每日计算，写入系统事件日志表 log_type=ALERT 或新增 USER_STATE）：

  指标 1：答题率
    定义：当日实际答题数 / 当日推送数
    正常范围：≥ 80%（每天 3 张答了至少 2-3 张）
    黄色阈值：连续 3 天 < 80%
    红色阈值：连续 7 天 < 50%

  指标 2：答题延迟
    定义：早报推送到第一条答题的时间差
    正常范围：< 4 小时（用户通常在上午/中午答题）
    黄色阈值：连续 3 天 > 8 小时
    红色阈值：连续 3 天 > 24 小时（当天没答，第二天才答）

  指标 3：不会率
    定义：当日"不会"答题数 / 当日总答题数
    正常范围：< 40%（大部分卡应该是"会"或"模糊"）
    黄色阈值：连续 3 天 > 50%
    红色阈值：连续 5 天 > 70%（用户面对的卡大部分都不会，说明难度太高或间隔太短）
```

**两级干预**：

```
黄色预警（任一指标连续 3 天触黄）：
  → 晚报中增加一条温和提示：
    「📊 本周你的答题率是 65%，比上周下降了。如果觉得复习压力大，可以说「暂停 2」
     把第 2 张卡暂停 3 天，或说「跳过 3」把第 3 张卡归档。」
  → 不自动改变任何设置，只提供选项

红色预警（任一指标触红，或两个指标同时触黄）：
  → 自动降低新卡引入量：从 1 张/日降到 0 张/日（只复习，不引入新卡）
  → 自动延长间隔：所有卡片的间隔乘以 1.5（给用户更多喘息空间）
  → 群内发一条明确提示：
    「⚠ 检测到你最近 7 天答题率只有 30%。系统已自动暂停新卡引入并延长复习间隔。
     当你连续 3 天答题率恢复到 80% 以上时，系统会自动恢复正常节奏。
     你也可以随时说「恢复」手动恢复。」
  → 红色预警的自动调整必须在 7 天后自动评估是否恢复，不能永久降速
```

**实现成本**：
- 三个指标的计算：从流水表统计，约 20 行代码
- 黄色预警的晚报提示：在晚报模板中增加条件分支，约 10 行代码
- 红色预警的自动调整：修改选题逻辑和间隔计算，约 30 行代码
- 新增指令「暂停 N」「恢复」：解析器扩展，约 15 行代码
- 合计：约 75 行代码 + 1 张表（或复用系统事件日志表的新 log_type=USER_STATE）

**与"宁可慢不可假"原则的一致性**：红色预警的自动降速是"慢"（减少学习量），不是"假"（不伪造任何数据）。且自动降速是可逆的——用户恢复后自动回到正常节奏。

**为什么这是 P2 而不是 P0/P1**：倦怠检测是"增强项"，不是"必须项"。系统没有倦怠检测也能正常运行，只是用户可能在 4 周后放弃。但如果用户已经用了 4 周还没放弃，说明倦怠风险低。**建议在波次 1（第 2–3 周）结束后再启用**——因为那时候用户已经过了"新鲜感期"，倦怠风险开始上升。

## 第十一章 🟡 N30：轻量知识关联机制（待拍板③）

### 11.1 问题陈述

V13 和 V13.1 的间隔重复是**单卡独立**的——每张卡的记忆曲线只取决于自己的复习历史，不考虑与其他卡片的关系。

**但人类记忆是关联网络**。当你复习"飞书自动化次数按动作计"时，如果你最近刚学过"飞书多维表格自动化有 200 次/月限制"，那张卡的记忆会被激活，复习效果更好。反过来，如果两张卡内容矛盾（比如一张说"按流程计"、一张说"按动作计"），同时复习会造成干扰。

V13.1 的池化校准（第 30 天用真实数据调整间隔）隐含了"卡片之间有差异"的假设，但**没有显式利用卡片之间的关联**。

### 11.2 对策：轻量关联（不建知识图谱，只用标签）

```
不建完整的知识图谱（成本太高，维护复杂），只用"标签"做轻量关联：

  学习卡表增列 `tags`（多选字段）
  每张卡可以打 1–3 个标签（如：飞书/自动化/API，间隔重复/学习科学，机电/空调/维保）

  关联利用方式（三种，从轻到重）：

  方式 1（P2 · 推荐）：同标签卡的复习间隔微调
    若用户今天复习了标签为 X 的卡 A，且答对了
    → 同标签的其他卡 B、C 的"下次复习日期"提前 1 天（利用激活扩散效应）
    → 提前幅度不超过间隔的 20%（防止过度调整）
    实现：derive 重算时，对每张卡检查"最近 3 天内是否有同标签的卡被答对"，有则微调

  方式 2（P2 · 可选）：同标签卡不连续推送
    早报选题时，避免 3 张卡全是同一个标签
    → 若 3 张卡中有 2 张同标签，第 3 张优先选不同标签的
    → 防止"连续复习 3 张飞书自动化的卡，脑子全是飞书"的干扰
    实现：选题逻辑增加标签多样性约束

  方式 3（P3 · 不推荐）：标签级掌握度
    计算每个标签的"平均掌握度"，当某标签的平均 M > 0.8 时，
    该标签的新卡引入优先级降低（因为用户已经掌握了这个领域）
    → 实现复杂，且标签质量参差不齐（用户可能懒得打标签），收益不确定
```

**为什么推荐方式 1+2，不推荐方式 3**：
- 方式 1 的"激活扩散"有学习科学依据（最近回忆过的相关内容会增强记忆），且实现简单（derive 增加一个查询）
- 方式 2 的"标签多样性"是常识性优化，实现更简单（选题时加一个过滤）
- 方式 3 的"标签级掌握度"需要用户认真打标签才能有效，但 V13 的用户可能懒得给每张卡打标签。如果标签质量差，标签级掌握度就是垃圾进垃圾出。

**待拍板③（✅ 已裁决：选甲案·启用方式1+2）**：是否启用知识关联？
- 甲：启用方式 1+2（推荐）
- 乙：只启用方式 2（标签多样性，不改间隔）
- 丙：不启用（保持单卡独立，最简单）

**若启用**，需要在 D1b 建表时增加 `tags` 字段（多选），并在使用手册中说明"建议每张卡打 1–3 个标签，标签用于优化复习顺序，不影响核心功能"。

**若不启用**，`tags` 字段可以延后到波次 1 再加（不阻塞 D1b）。

## 第十六章 结论

### 16.1 三句话总结

1. **设计与方向连续第四轮无需改动** —— 事件溯源、文字指令主路径、INIT Seed、Coze 第三顺位、11 张表、跨日门槛、event_id=message_id、回执三态、日志四合一，本轮全部作为前提采纳。债务已从"设计层"→"施工图精度"→**"施工到第三步的三阶坑"**。
2. **V13.1 的对策本身会引入三阶问题** —— 回执三态没有告警去重会刷屏、event_id=message_id 遇到撤回消息留孤儿记录、hash 自检不匹配时系统直接变砖、公式字段可能被 derive 静默覆盖。本轮把这 12 个三阶坑填上，并把 6 个半拉子工程（错因后状态机、回滚 SOP、TCO、分区 TTL、倦怠检测、知识关联）补成闭环。
3. **本轮提升高度集中在维护简易性和可落地性** —— 维护简易性 4.64→4.95（+0.32，接近满分），可落地性 4.64→4.77（+0.14），知识转化 4.41→4.55（+0.14）。总均 4.56→4.66（+0.09），待验证项通过后 4.67。

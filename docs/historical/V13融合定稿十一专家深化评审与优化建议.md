## 第一章 🔴→🟢 工程硬伤一：飞书自动化次数被低估一倍 —— **已由用户裁决①解除为监控项**

### 1.1 问题陈述

原评审 §4.2 与 §11.5 给出关键推导：

> 按钮路径每日 3 张 × 2 键 × 30 天 = **180 次/月**，基础版 200 次/月必然超限

这个推导**隐含了一个未经核验的假设：一次按钮点击 = 消耗 1 次自动化运行次数**。

**但按定稿 D3 晚的表内按钮设计，按钮触发的自动化的动作是：**

```
动作1：更新记录（改「卡片状态」「上次复习日期」等派生字段）
动作2：发送消息（推送回执「✓ 下次 X 月 X 日」）
```

这是**两个动作**。在飞书多维表格自动化中，一个自动化流程包含多个动作时，**运行次数的计量口径需要实测确认**——存在两种可能：

| 口径 | 一次点击消耗 | 月度（3张×2键×30天=180次点击） | 基础版 200 次/月 |
|---|---|---|---|
| A：按**流程**计（原评审假设） | 1 次 | 180 次 | 勉强够（余 20 次） |
| B：按**动作**计（我判断更可能） | **2 次** | **360 次** | **第 10 天即耗尽** |

### 1.2 为什么我判断是口径 B（按动作计）

1. 飞书多维表格自动化的计费单位是"自动化运行次数"，而一个流程里的每个动作都是一次服务端执行
2. 原评审自己也提到"叠加 5 个 enabled 工作流后基础版必然超限"——说明已有认知是**动作级**消耗
3. **最关键的**：即便按口径 A，180 次点击 + 5 个已有工作流也已在爆边缘；按口径 B，则第 10 天断供

## 第二章 🔴→🟢 工程硬伤二：事件溯源的冷启动——存量 23 张卡零流水 —— **已由用户裁决②彻底关闭**

### 2.1 问题陈述

定稿范式是**事件溯源**：

```
「复习流水表」只追加 → review_derive.py 从流水重算 → 学习卡片表全部派生字段
```

原评审 §11.2 D1 晚要求：

> 建「复习流水表」+ 学习卡新字段；**23 张存量只标状态不伪造日期**

**这里有一个致命缺口**：23 张存量卡**没有任何历史流水**。`review_derive.py` 从空流水重算，结果只能是：

```
23 张卡 → 状态全部 = NOT_STARTED
```

而 `NOT_STARTED` 的卡，按教育专家定稿"到期卡优先 + NOT_STARTED 新卡补足到 3 张"——**它们会被当作"新卡"重新引入队列**。

**后果**：
- 用户已经学过若干张卡，系统却把它们当新卡
- 若为避免此问题而"手工标注状态"，则**状态有了两个真源**（手写的状态字段 + derive 从流水重算的状态），**直接违背事件溯源"单一真源"的根本原则**，且下一次 `--rebuild-all` 会把手工标注全部覆盖掉

> **这是范式切换的必然代价**：从"状态字段"切到"事件溯源"，存量数据必须有一套**播种（seed）策略**，否则存量就是孤儿数据。

### 2.2 【已裁决采纳】对策：Seed Event（种子事件）

> **用户裁决②（2026-09-10）**：✅ **接受**为 23 张存量卡写 INIT 种子流水。
> 本节以下方案从"建议"转为**待执行方案**，D1b 晚直接施工。

在「复习流水表」建表当天，为 23 张存量卡各写入**一条初始化流水**：

```
event_id = {card_id}|INIT|{建表时间戳}
卡片ID   = {card_id}
结果     = INIT          ← 新增枚举值，不是 会/不会/模糊
时间戳   = 建表时间（或卡片创建时间，取较晚者）
来源     = SEED_MIGRATION
```

**关键边界约束（必须写进 derive 逻辑与契约测试）**：

| 约束 | 说明 |
|---|---|
| INIT **不计入**连续正确次数 | 它不是一次"答对" |
| INIT **不参与**跨日门槛计算 | 不影响"跨≥3 自然日"判定 |
| INIT **不影响**掌握度 M | 掌握度只由真实反馈派生 |
| INIT **不算**"上次复习日期" | 卡片仍为 NOT_STARTED，按新卡引入 |
| INIT **可被** `--rebuild-all` 重放 | 重放后结果与首次一致（幂等） |

### 2.3 为什么这不违反"不伪造复习记录"

| 伪指标做法（❌ 禁止） | Seed Event（✅ 本方案） |
|---|---|
| 把「上次复习日期」填成创建日期 → 制造 20 条虚假复习记录 | 只记录"这张卡于 X 日进入系统"这一**客观事实** |
| 掌握度/记忆保持率基于假数据计算 | 掌握度仍为 0，不受污染 |
| 事后无法区分真假 | `结果=INIT` 显式可查，永不混淆 |

**本质区别**：Seed 记录的是**事实（卡片入库）**，伪造记录的是**行为（用户复习过）**。

### 2.4 无 Seed 方案的替代选项（若坚持"零历史"）

| 方案 | 做法 | 代价 | 状态 |
|---|---|---|---|
| **甲** | Seed Event | 23 条 INIT 流水，5 分钟 | ✅ **用户已裁决采纳** |
| 乙 | 存量卡全部标记 `ARCHIVED`，只用新卡重启 | 丢弃 23 张卡的历史价值 | ❌ 已否决 |
| 丙 | 单独维护一个"存量卡初始化日期"字段 | 双真源，违背事件溯源 | ❌ 已否决 |

**执行口径（已定）**：23 张卡全量 Seed，不做目标覆盖矩阵初筛（P2-6 的"初筛后再 Seed"降级为可选优化，不阻塞 D1b）。

### 2.5 验收标准

```
1. 流水表 23 条 INIT 流水（来源=SEED_MIGRATION）
2. review_derive.py --rebuild-all 后，23 张卡状态全为 NOT_STARTED
3. 契约测试新增⑫：含 INIT 流水的重算，状态/连续正确/掌握度均不受污染
4. 手工改一张卡的状态 → 再次 --rebuild-all → 状态被 derive 覆盖回 NOT_STARTED
   （证明单一真源生效，手工标注无效）
```

### 12.2 核心意见

**意见 1：题量降级后，学习节奏要重新设计**

若因基础版降到**每日 1 张**，则：
```
每日 1 张 × 30 天 = 30 张/月
23 张存量卡 → 约 3 周才能全部引入一遍
```
这**不是问题**——间隔重复本来就不追求"全覆盖速度"，而追求"每张卡在恰当间隔被复习"。**但要向用户说清预期**，否则用户会以为"系统只给我 1 张，是不是坏了"。

**建议在使用手册明确写**：
> 每日题量由你的飞书版本决定（基础版 1 张 / 专业版 3 张）。题量少不是缺陷——间隔重复的效果取决于**复习时机是否恰当**，而不是每日刷多少张。

**意见 2：INIT 卡片的首次学习体验**
Seed 后卡片是 `NOT_STARTED`，首次引入时应按**新卡**处理：
- 先展示完整问答（不是直接考）
- 标记"会/不会"后进入正式间隔循环
避免用户面对一张完全陌生的卡直接被"考"。

**意见 3：跨日门槛在"每日 1 张"下的可行性检查**
```
连续正确 ≥3 且 跨 ≥3 自然日 且 最长间隔 ≥3 天
每日 1 张 → 最快 3 天答对 3 次 → 满足"连续≥3"与"跨≥3日"
但"最长正确间隔 ≥3 天"需要：第1天对 → 间隔2天 → 第3天对 → 间隔4天 → 第7天对
                             → 最长间隔 = 4 天 ≥ 3 ✅ 可满足
```
**结论：每日 1 张不影响跨日门槛达成**（最长间隔由间隔表驱动，与题量无关）。这一点原方案没说明，容易让人误解题量会影响升级。

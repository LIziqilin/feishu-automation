## 第一章 交互重构：从序号制到顺序消费制（修 X5 + X9）

### 1.1 序号制的问题

序号制（「会 2」）要求用户：看早报 → 记住编号 → 打字。这是**三步认知 + 一次记忆负担**。群里有早报、晚报、告警等多条消息滚动，编号参照极易错乱。

更严重的是 X9：飞书群是线性文本，不支持折叠答案。如果早报只推问题，用户想不起答案只能瞎猜；如果推问题+答案，用户直接看答案，自测失效。**合意困难（先自测后看答案）这个学习科学核心机制没有载体。**

### 1.2 重构：顺序消费 + 答案分离

**早报格式改造**（每条独立一条消息，便于引用）：

```
📇 今日复习 1/3
Q：飞书多维表格自动化次数怎么算？
（答完后我会告诉你答案和下次复习时间）
──────────
直接回复：会 / 不会 / 模糊
```

**关键改造点**：

1. **答案不在早报里**：用户答完 → 系统回执时才给答案（自测成立 ✓）
2. **不带序号**：早报按条推送，用户**直接回「会」「不会」「模糊」**，系统按当日推送顺序依次消费
3. **每条独立消息**：便于引用/回复，避免编号错乱
4. **回执含答案**：

```
✓ 已记录：不会
💡 答案：按流程计还是按动作计需实测确认，1流程含2动作时可能计1次或2次
📅 下次复习：09-14（3天后）
```

### 1.3 顺序消费制的实现规则

```
【消费规则】
  1. 早报按顺序推送 3 张卡（卡1→卡2→卡3），每条独立消息
  2. 用户回复「会」「不会」「模糊」（不带编号）→ 系统消费当前待答的第一张卡
  3. 消费完卡1后，下一条无编号回复消费卡2，以此类推
  4. 3 张全部消费完后，无编号回复视为闲聊（静默丢弃）

【当前待答卡的追踪】
  系统维护 current_card_index（0/1/2），记录当前待答的是第几张
  用户每消费一张，index + 1
  次日早报推送时重置为 0

【兜底：保留显式编号（可选）】
  若用户想跳答，仍支持「会 3」「不会 2」
  规则：有编号按编号，无编号按顺序消费
  两种并存，不冲突

【重新获取今日卡片】
  用户发「今日卡片」或「卡片」→ 系统重新推送今日 3 张卡的问题
  （解决场景 B：开会时收到早报，晚上才答，早报刷上去了）
```

### 1.4 为什么这比序号制好

| 维度 | 序号制「会 2」 | 顺序消费制「会」 |
|---|---|---|
| 用户认知步数 | 看编号→记编号→打字（3步） | 直接打字（1步） |
| 记忆负担 | 要记哪张是几号 | 无 |
| 群消息滚动影响 | 编号错乱 | 无影响（按顺序消费） |
| 合意困难 | 无法落地（线性文本） | **回执时才给答案 ✓** |
| 手机端打字量 | 3-4 字符 | 1-2 字符 |
| 跳答能力 | 支持 | 支持（显式编号兜底） |

**代价**：用户不能跳着答（必须先答第1张才能答第2张）。但每天只有 3 张，顺序答完全合理。显式编号兜底保留了跳答能力。

## 第二章 9 个关键缺陷修复

### 2.1 X2 + X4：冷启动拼图修复 — Seed 时分配 intro_offset 错峰引入

**问题**：
- X2：Seed 写入 result=INIT，NOT_STARTED 卡「上次复习日期」为空。公式 #5 = `IF(状态="MASTERED","",上次复习日期+间隔天数)` → 空值参与运算，返回什么？未定义。23 张卡要么全到期（灾难）要么永不到期（闭环死）。
- X4：23 张存量卡都算新卡，1 张/日 → 前 23 天每天只推 1 张，"每日 3 张"预期落空，队列空转。

**修复（推荐 B：错峰引入）**：

```
【Seed 时给每张卡分配 intro_offset】
  23 张存量卡按优先级排序，分配 intro_offset = 0~22 天
  （优先级由用户指定，或按卡片重要性排序）

  学习卡表增列 intro_offset（数字，默认 0）
  Seed 时写入每张卡的 intro_offset

【公式 #5 改为（三分支）】
  下次复习日期 =
    IF(状态="MASTERED", "",
       IF(状态="NOT_STARTED", 入库日期 + intro_offset,
          上次复习日期 + 间隔天数))

  入库日期 = Seed 写入日期（固定为系统上线日）

【队列效果】
  第 1 天：intro_offset=0 的卡到期（1 张新卡）+ 无已引入卡复习 → 推 1 张
  第 2 天：intro_offset=1 的卡到期（1 张新卡）+ 第 1 天的卡复习 → 推 2 张
  第 3 天：intro_offset=2 的卡到期（1 张新卡）+ 前 2 天的卡复习 → 推 3 张 ✓
  第 4~23 天：每天 1 张新卡 + 已引入卡复习 → 稳定 3 张 ✓
  第 24 天起：23 张全部引入，纯复习队列 → 稳定 3 张 ✓

  队列永远有 3 张，不空转也不爆炸

【存量卡不占用新卡配额】
  intro_offset 引入的存量卡 ≠ 新卡
  新卡上限 1 张/日（N35）只适用于用户后续手动创建的 NOT_STARTED 卡
  存量卡通过 intro_offset 错峰引入，不占用新卡配额
  → X4 修复：前 23 天不是每天只推 1 张，而是第 3 天起稳定 3 张
```

**验证标准**：
- Seed 后 23 张卡都有 intro_offset（0~22，不重复）
- 公式 #5 对 NOT_STARTED 卡返回"入库日期+intro_offset"，不为空
- 模拟第 1~30 天的选题，第 3 天起每天稳定 3 张
- 存量卡引入不触发 last_new_card_date 更新（不占用新卡配额）

### 2.2 X3：回执时序矛盾修复 — 回执拆两段

**问题**：回执要含"下次复习日期"，但那是公式字段 #5，derive 同步写入后公式还没重算完（飞书最终一致性）。回执拿不到日期，或产生双真源。

**修复（推荐 B：回执拆两段）**：

```
【回执拆两段】
  第一段（即时，<3s）：derive 写入后立即回
    ✓ 已记录：不会
    （确认用户动作已被接收，满足即时反馈需求）

  第二段（延迟，<10s）：derive 写入后 sleep 500ms，读回公式字段值，再回
    💡 答案：按流程计还是按动作计需实测确认…
    📅 下次复习：09-14（3天后）

  或合并为一条：sleep 500ms 后一次性回完整回执（<1s，用户可接受）

【为什么不选 A（derive 自己算一遍）】
  derive 自己算"下次复习日期" → 与公式字段双真源，违背字段分类表
  如果 derive 算的和公式算的不一致，用户不知道信哪个

【为什么不选 C（取消公式字段，全部 derive 计算）】
  这是长期推荐方案（见 2.3），但本轮先采用 B 作为过渡
  2.3 会把所有公式字段改为写入字段，届时回执直接读 derive 写入的值，无延迟
```

**验证标准**：
- 用户发「会」后 3s 内收到第一段回执（✓ 已记录）
- 10s 内收到第二段回执（答案+下次日期）
- 回执中的"下次复习日期"与学习卡表公式字段值一致
- derive 不自行计算"下次复习日期"（避免双真源）

### 2.3 X6：untrusted 与公式字段冲突修复 — 公式字段全部改为写入字段

**问题**：untrusted=TRUE 要"计入累计复习次数但不计入 M"，但"累计复习次数"是公式字段 COUNTIF，**飞书公式无法按 untrusted 过滤**（COUNTIF 单条件）。

**修复（推荐：全部公式字段改为写入字段）**：

```
【原字段分类表（V13.3/V13.4）】
  6 个写入字段 + 2 个公式字段（#5 下次复习日期、#7 累计复习次数）

【新字段分类表（V13.5）】
  8 个写入字段 + 0 个公式字段
  原公式字段 #5 #7 全部改为写入字段，由 derive 计算写入

【#5 下次复习日期（改为写入字段）】
  derive 计算：下次复习日期 = 上次复习日期 + 间隔天数
  MASTERED 状态 → 下次复习日期 = 空（不复习）
  NOT_STARTED 状态 → 下次复习日期 = 入库日期 + intro_offset（见 2.1）
  derive 每次重算时写入，无公式延迟

【#7 累计复习次数（改为写入字段）】
  derive 计算：累计复习次数 = COUNT(流水 WHERE 卡片ID=本卡 AND result<>'INIT'
                                      AND superseded=FALSE)
  untrusted=TRUE 的记录：计入此数（因为用户确实复习了）
  superseded=TRUE 的记录：不计入（已被撤回/编辑）
  derive 全量掌控，无冲突

【为什么全部改为写入字段】
  1. 消除 X3 回执时序矛盾（derive 写入后立即可读，无公式延迟）
  2. 消除 X6 untrusted 过滤冲突（derive 可按任意条件过滤）
  3. 消除"公式 vs derive"双真源风险（单一真源 = derive 从流水重算）
  4. 飞书公式能力有限（COUNTIF 单条件、不支持复杂逻辑），derive 用 Python 计算更灵活

【代价】
  飞书表内不再自动计算，全靠 derive
  → 但 derive 有即时触发（N33）+ 09:07 兜底，数据始终最新
  → 用户在表内手动修改写入字段会被下次 rebuild 覆盖（符合单一真源原则）
```

**验证标准**：
- 学习卡表无公式字段，全部为写入字段
- untrusted=TRUE 的记录计入累计复习次数，但不计入 M/连续正确
- superseded=TRUE 的记录不计入累计复习次数
- derive 写入后立即可读"下次复习日期"，无公式延迟
- 回执中的"下次复习日期"直接读 derive 写入值，无需 sleep

### 2.4 X7：REVOKE 与 event_id 幂等冲突修复 — revoke_of 字段

**问题**：event_id=message_id 且 UNIQUE；撤回时追加 REVOKE 流水，event_id=`{message_id}|REVOKE|{ts}` → 同一 message_id 有两条不同 event_id，**UNIQUE 失效**。

**修复**：

```
【幂等键保持为 message_id】
  event_id = message_id（不变，UNIQUE 约束不变）
  撤回不创建新的 event_id

【REVOKE 用独立字段】
  流水表增列 revoke_of（文本，可空）
    → 指向被撤回的原始流水的 event_id
  流水表增列 event_type（单选：COMMIT / REVOKE，默认 COMMIT）
    → 区分正常流水和撤回流水

  撤回时：
    1. 原始流水的 superseded 改为 TRUE（标记为已被撤回）
    2. 追加一条新流水：
       event_id = {message_id}|REVOKE|{ts}（新的唯一 ID，不与原始 message_id 冲突）
       event_type = REVOKE
       revoke_of = 原始流水的 event_id
       结果 = REVOKE
       时间戳 = 撤回时间

  → event_id 仍然 UNIQUE（因为 REVOKE 流水的 event_id 包含 |REVOKE| 后缀，与原始 message_id 不同）
  → 原始 message_id 的 COMMIT 流水只有一条，UNIQUE 不失效
  → revoke_of 字段建立 REVOKE 与原始流水的关联

【derive 处理】
  derive 重算时：
    event_type=REVOKE 的流水 → 找到 revoke_of 对应的原始流水 → 标记原始流水 superseded=TRUE
    → superseded=TRUE 的流水不参与任何计算（见 2.5）
```

**验证标准**：
- event_id 列 UNIQUE 约束不失效（REVOKE 流水有唯一的 event_id）
- 撤回后原始流水 superseded=TRUE
- REVOKE 流水的 revoke_of 指向原始流水的 event_id
- derive 重算时排除 superseded=TRUE 的流水
- 契约测试：撤回后累计复习次数不包含被撤回的记录

### 2.5 X8：6h 宽限期与跨日门槛叠加修复 — superseded 不参与任何计算

**问题**：6h 内取末次（superseded），但跨日升级要求"跨 ≥3 个自然日"。被 superseded 的流水还参与自然日计数吗？

**修复（明确定义）**：

```
【superseded 流水不参与任何计算】
  superseded=TRUE 的流水：
    ❌ 不计入连续正确次数
    ❌ 不计入 M 值计算
    ❌ 不计入间隔天数计算
    ❌ 不计入累计复习次数
    ❌ 不参与"跨 3 个自然日"升级门槛计数
    ❌ 不参与 6h 宽限期判定（6h 宽限期只用于判定是否 supersede，不参与后续计算）
    ✅ 仅保留在流水表中（事件溯源只追加，不删除）

【跨日升级门槛的"3 个自然日"定义】
  = 3 个有有效（非 superseded）作答的自然日
  例：
    第 1 天答「会」（有效）
    第 2 天答「会」后撤回（superseded，不计入）
    第 3 天答「会」（有效）
    第 4 天答「会」（有效）
    → 有效作答日 = 第 1、3、4 天 = 3 个自然日 → 满足跨日升级门槛
    → 第 2 天的撤回不计入，但不影响其他天的计数

【6h 宽限期只用于判定是否 supersede】
  6h 宽限期的作用：判定同一 card_id 的两条作答是否为"同一次复习的修改"
  → 若是，较早的一条标记为 superseded
  → 标记完成后，6h 宽限期不再参与任何后续计算
  → superseded 的流水不参与跨日门槛计数（因为它已经被"修改"了，不是有效作答）
```

**验证标准**：
- superseded=TRUE 的流水不参与任何 derive 计算
- 跨日门槛只计数有有效作答的自然日
- 6h 宽限期只用于 supersede 判定，不参与后续计算
- 契约测试：第 2 天撤回后，跨日门槛计数不包含第 2 天

## 第三章 异常路径的用户侧反馈（补前五轮最大空白）

> 前五轮只定义了 happy path（用户完美地打了正确指令）。本章补齐所有异常路径的**用户侧回执**——这是"宁可慢不可假"的核心：**任何用户主动发起的动作，必须有回执。静默失败是头号敌人。**

### 3.1 完整回执矩阵

| 场景 | 系统动作 | 用户收到的回执 | 回执时限 |
|---|---|---|---|
| 解析成功（顺序消费） | 写流水 + derive | `✓ 已记录：会` + `💡 答案：…` + `📅 下次复习：09-14` | <3s（第一段）/ <10s（完整） |
| 解析成功（显式编号「会 3」） | 写流水 + derive | `✓ 已记录第3张：会` + 答案 + 下次日期 | <3s |
| 解析失败（格式不对「会 一」） | 记错例，**不写流水** | `❓ 没看懂「会 一」，请发：会/不会/模糊（或「会 2」指定编号）` | <3s |
| 非指令消息（闲聊「天气不错」） | 静默丢弃，**不记错例不告警** | 无 | — |
| 批量部分失败（「会 1 会 2 会 3」第2张失败） | 成功的写入，失败的标记 | `✓ 会1 已记 / ❓ 会2 没看懂 / ✓ 会3 已记` | <5s |
| 撤回消息 | 追加 REVOKE，原始流水 superseded=TRUE | `↩️ 已撤销刚才的记录` | <3s |
| 编辑消息（内容仍符合指令） | 原解析 superseded，按新内容重新解析 | `✓ 已更新：不会`（覆盖原记录） | <3s |
| 编辑消息（内容不符合指令） | 原解析 superseded，视为撤回 | `↩️ 已撤销刚才的记录（编辑后不再是答题指令）` | <3s |
| 权限失效 | 告警（去重后） | `🔴 权限失效，答题暂不记录。首次发现：02:00，持续：1h15min。建议：检查自建应用 im:message 权限` | 立即（首次）/ 每小时摘要 |
| hash 不匹配（B 档） | 写 untrusted | `⚠ 已记录但标记为待核对，不影响你的复习。修复 sdk 后回复「转可信全部」即可恢复` | <3s |
| untrusted 转可信 | untrusted→FALSE + derive 重算 | `✅ 已将 3 条记录转为可信，已触发 3 张卡片的派生值重算` | <5s |
| 队列空（无卡可推） | 不推送 | `📭 今日无待复习卡片` | 早报时间 |
| 新卡引入 | NOT_STARTED→LEARNING + INIT 流水 | `🆕 今日新卡：[卡片标题]` | 早报时间 |
| 倦怠黄色预警 | 晚报提示 | `📊 本周答题率 65%，比上周下降。觉得压力大可以说「暂停 2」` | 晚报 |
| 倦怠红色预警 | 自动降速 + 通知 | `⚠ 检测到最近 7 天答题率 30%，已自动暂停新卡并延长间隔。连续 3 天恢复后自动正常` | 立即 |
| 冷归档触发 | 间隔×3 + 优先级降权 | `📦 卡片 [标题] 已完全掌握，进入冷归档（间隔延长至 90 天）` | derive 重算时 |
| derive 主触发失败 | 记录 ALERT，09:07 兜底 | （不打扰用户，09:07 兜底自动修正） | — |

### 3.2 回执铁律

```
【铁律 1】任何用户主动发起的动作，必须有回执
  用户发了消息（无论是答题还是指令），系统必须在 3s 内回复
  即使是解析失败，也要回「❓ 没看懂」
  静默失败 = 用户以为成功了 = 数据丢失 = 违反"宁可慢不可假"

【铁律 2】回执必须包含"系统做了什么"
  ✓ 已记录：会 → 用户知道系统记录了什么
  ❓ 没看懂 → 用户知道系统没记录，需要重发
  ↩️ 已撤销 → 用户知道撤回生效了
  不允许只回一个"收到"而不说明做了什么

【铁律 3】非用户主动发起的动作，按需回执
  告警、倦怠预警、冷归档通知 → 需要回执（让用户知道系统状态变化）
  derive 主触发失败、TTL 清理 → 不需要打扰用户（后台自动处理）
  原则：影响用户体验的变化必须通知，不影响的静默处理

【铁律 4】回执语言简洁、口语化
  不使用技术术语（如"event_id""superseded""untrusted"）
  用用户能理解的语言："已记录""没看懂""已撤销""待核对"
  每条回执不超过 3 行（手机端一屏可见）
```

185	### 2.3 为什么单点估算会系统性偏低
186	
187	三点估算里 P（悲观值）与 M（最可能值）的比值普遍在 2–3 倍，且悲观情形都不是假想的：
188	
189	- "查 `im:message` 权限"的 P=30min —— 因为开放平台的权限页需要先确认自建应用归属、可能遇到"权限已申请但未发版生效"的中间态
190	- "建学习卡 8 字段"的 P=50min —— 字段类型（单选枚举、日期、公式、关联）各有坑，公式字段还可能需要反复试
191	- "27 任务双跑排查"的 P=40min —— 本地 13 + 云端 14 分处两套系统（任务计划程序 + GitHub Actions），比对需要来回切
192	
193	**上一版用单点估算，等于默认所有动作都走 M 路径**，这在"第一次做、且要边找入口边操作"的场景下不成立。

205	> **诚实标注**：乙案不是"变快了"，是"把活分摊了"。总工时 6.3h 一分未减，只是从第 1 周挪 1h 到第 2 周。

207	### 2.5 附带修订：D1 拆**三**晚而非两晚
208	
209	上一版拆 D1a/D1b。本轮三点估算显示 D1 预算 216.7min，若拆两晚则每晚 1.8h —— 仍超出"一晚 30–60min"的可执行区间，且第二晚会同时混着"建表"和"写数据/定规则"两类性质不同的工作。
210	
211	```
212	D1a（86min ≈ 1.4h）核查类：只读，零风险，可中断
213	  → 产出：权限结论 + 次数口径 + 双跑清单
214	D1b（79min ≈ 1.3h）建表类：结构变更，可回滚
215	  → 产出：三张表（流水表 / 学习卡新字段 / 检索日志表）
216	D1c（52min ≈ 0.9h）数据与规则类：写入 + 约定
217	  → 产出：23 条 Seed + 单活规则 + event_id 定义 + 幂等表
218	```
219	
220	**分类原则**：按"失败了会怎样"分晚 —— 核查类失败无损失，建表类失败可删表重来，写入类失败需清理数据。同一晚不混两类，避免"建到一半发现权限没有"的返工。
221	
222	> 这与上一版第三章的原则"能脚本化的绝不 GUI，能延后的绝不挤进第一晚"一脉相承，只是把"两晚"修正为"三晚"。

231	### 3.1 🆕 意见 1（P1 · N14）：文字指令主路径必须建"回执三态"
232	
233	原方案 1.3 节准确指出按钮路径的历史病是**静默失败**（"自动化超限通常不报错，用户以为点了没用 → 重演 20/23 卡片为空"）。裁决①把主路径换成文字指令后，**这个病没有消失，只是换了载体**：
234	
235	```
236	文字指令的静默失败场景（原方案未覆盖）：
237	  ① 用户打了「会 1」，但轮询周期还没到 → 用户以为没生效，又打一遍
238	  ② im:message 权限到期/被回收 → 轮询静默读不到消息，用户完全无感
239	  ③ 解析器不认识「会1」（无空格）或「会 一」（中文数字）→ 消息被丢弃
240	  ④ 卡片序号 1 在今日队列里已过期（跨日）→ 写入被拒，但用户不知道
241	```
242	
243	**四种场景全都不报错，用户侧表现都是"我答了但系统没反应"** —— 与按钮路径的静默失败**完全同构**。
244	
245	**对策：回执三态可观测**
246	
247	```
248	每一条被读到的群消息，必须落到以下三态之一，缺一不可：
249	
250	  态1 RECEIVED   —— 轮询读到该 message_id
251	  态2 PARSED     —— 正则解析出 (卡片序号, 结果)
252	  态3 COMMITTED  —— 已写入流水表且拿到 event_id
253	
254	告警规则：
255	  态1 有、态2 无（超过 2 个轮询周期） → 解析失败告警，附原始消息文本
256	  态2 有、态3 无                     → 写入失败告警，进死信队列
257	  某日态1 总数 = 0 且用户确有答题     → 权限/轮询失效告警（最高级）
258	
259	落点：指令处理日志表（可与检索日志表同批建，都是只追加）
260	```
261	
262	**为什么这是 AI 工程层的职责**：影子对账保护的是"derive 不静默污染派生值"，回执三态保护的是"用户输入不静默丢失"。两者一前一后，才构成完整链路。**原方案只做了后半段。**
263	
264	### 3.2 🆕 意见 2（P0 · 影响稳定性）：event_id 用 `message_id`，不要用时间戳
265	
266	原方案 1.4.3 只写了"两条路径共用同一个 `event_id` 生成规则与幂等表"，**但没定义规则是什么**。第二章给 Seed 定义了 `{card_id}|INIT|{建表时间戳}`，容易被顺势类推成 `{card_id}|{结果}|{时间戳}`。**这个类推是错的**：
267	
268	```
269	❌ 若 event_id = {card_id}|{结果}|{时间戳}
270	   轮询重试 / 补发 / 进程重启后重读同一条消息
271	   → 时间戳变了 → event_id 变了 → 幂等表拦不住 → 双写重演
272	   （这正是 V11 obsidian_sync 双注册的机制）
273	
274	✅ event_id = {message_id}
275	   飞书每条群消息有全局唯一且稳定的 message_id
276	   → 无论重读多少次，event_id 恒定 → 天然幂等
277	   → 幂等表只需一列 UNIQUE 约束即可
278	```
279	
280	**按钮路径的对应规则**：按钮回调同样带唯一标识（回调 event_id 或 record_id + 操作时间），**不可用"点击时刻的本地时间戳"**。两条路径各自用平台提供的稳定 ID，才叫"共用同一个生成规则"—— 共用的是**规则形态**（用平台稳定 ID，不用自造时间戳），不是字符串模板。
281	
282	### 3.3 🆕 意见 3：当日重复作答的语义必须定义
283	
284	`event_id = message_id` 解决了"同一条消息不被重复写入"，但没解决"用户当天改主意"：
285	
286	```
287	09:00 用户打「不会 2」→ 写入 event_A
288	09:05 用户打「会 2」  → 写入 event_B（不同 message_id，两条都合法）
289	
290	derive 重算时该取哪条？
291	```
292	
293	**建议口径**：**同一自然日内，同一 card_id 取时间戳最后一条为准**（符合"用户改主意"的直觉），但**两条流水都保留不删**（事件溯源只追加原则）。即：流水层全留，派生层取末次。
294	
295	这条必须写进契约测试（建议新增 **⑭ 当日重复作答，派生结果取末次且流水不被删除**）。

312	### 4.1 🆕 意见 1（P1）：三顺位之间要有"探测"，不能只有"降级"

318	```
319	
320	但**没有定义"怎么判断该降到下一顺位"**。三种触发条件混在一起，各自的探测方式完全不同：
321	
322	| 顺位 | 失效条件 | 探测方式 | 探测成本 |

333	③ 顺位切换写日志：何时从 1° 降到 2°、原因是什么、持续多久
334	   → 这张日志就是"系统实际在用哪个 AI"的唯一真源
335	```

339	### 4.2 🆕 意见 2：告警线公式补"日均怎么算"
340	
341	原方案给了 `余额 → 天数 = 余额 / 日均`，三级阈值（<7 黄 / <3 橙 / =0 红）很清楚。但**"日均"的口径没定**，而这直接决定告警是否误报：
342	
343	```
344	❌ 日均 = 总消耗 / 使用天数
345	   → 若系统前 3 天调试期狂跑、后 20 天正常使用，日均被调试期拉高 → 长期误报橙色
346	❌ 日均 = 昨日消耗
347	   → 单日波动（比如某天做了一次批量嵌入）就触发降级 → 抖动
348	
349	✅ 建议：日均 = 最近 7 天的中位数消耗
350	   → 抗单日尖峰，且比均值更稳健
351	   → 冷启动期（不足 7 天）用"最近 3 天均值 + 系数 1.5"作保守估计，并标注 COLD_START
352	```
353	
354	**这与第二章 Seed 的"冷启动"是同一类问题**：任何基于历史统计的阈值，都必须定义"历史不足时怎么办"。原方案在数据层想到了（Seed），在告警层没想到。

359	
360	```
361	只记命中 → 能知道"哪些问题被答上了"
362	         → 不知道"哪些问题问了但没答上"
363	         → 池化校准时无法识别知识盲区，只能优化已有内容的排序
364	
365	建议检索日志表增两列：
366	  hit_count     命中条数（0 表示未命中）
367	  fallback_level 最终由第几顺位回答（1/2/3/4）
368	```
369	
370	**`hit_count = 0` 的记录才是最有价值的**：它直接指出知识库缺什么。这批数据喂给池化阶段一，比命中数据的价值高一个量级。

387	
388	### 5.1 🆕 意见 1（P0 · 细化阻断项）：`im:message` 不是一个权限，是**三档**
389	
390	原方案 1.4.1 把 D1a 的动作定义为"查自建应用是否已具备 `im:message` 权限"，结论分"有/无/被拒"三支。**这个二分法在飞书开放平台的实际权限模型下不够用**：
391	
392	| 档位 | 权限范围 | 用户交互约定 | 审核难度 |
393	|---|---|---|---|
394	| **A** | 仅接收 **@机器人** 的群消息 | 用户必须打 `@机器人 会 1` | 低（常见） |
395	| **B** | 接收群内**全部**消息 | 用户直接打 `会 1`，无需 @ | 高（涉及群隐私，审核严） |
396	| **C** | 无消息读取权限 | 只能走按钮路径 | — |
397	
398	**三档对应三份不同的使用手册**，而原方案的分支 A/B/C 是按"有/无/被拒"划分的，**无法区分 A 与 B**。若实际拿到的是 A 档而手册按 B 档写，用户打 `会 1` 不 @ 机器人，系统将完全收不到 —— 且**不报错**，直接落进 3.1 描述的静默失败。
399	
400	**修订后的 D1a 权限核查（三分支 → 四分支）**
401	
402	```
403	查自建应用消息读取权限档位：
404	
405	  分支 A：拿到 B 档（全量群消息）
406	    → 手册写"直接打 会 1"，最省事，便捷性最优
407	  分支 A'：拿到 A 档（仅 @机器人）🆕
408	    → 手册写"必须 @机器人 会 1"
409	    → 早报模板需内置 @机器人 的提示文本，降低用户记忆负担
410	    → 便捷性略降（多一次 @），但仍不占自动化次数
411	  分支 B：无任何消息读取权限
412	    → 立即申请，审核期回退按钮路径
413	  分支 C：申请被拒
414	    → 永久回退按钮路径 + 题量按次数口径定
415	```
416	
417	**这是本轮对可落地性最实质的一处补强**：原方案把"权限"当布尔值，实际它是枚举值，且枚举结果直接决定用户每天要打什么字。

419	### 5.2 🆕 意见 2（P1 · 便捷性）：**批量文字指令**是比交互卡片便宜得多的改进
420	
421	原方案 0.2 节诚实标注了裁决①的代价：**便捷性 −0.14**，归因"打字（`会 1`）比点按钮多一步"。第六章把改进希望寄托在"群交互卡片（P1，未来）"上。

424

427	  「会 1」「不会 2」「会 3」     → 3 次输入 + 3 次发送

429	批量：1 条消息答完 3 张

433	解析器成本：正则从 r'(会|不会|模糊)\s*(\d+)' 扩展为支持多组
434	           → 约 15 行代码，无新增权限、无新增表、无新增调度
435	```

437	**三档路径的真实成本对照**
438	
439	| 路径 | 用户动作数 | 开发成本 | 权限依赖 | 自动化次数 | 上线时机 |
440	|---|:---:|:---:|---|:---:|---|
441	| 单条文字指令（现状） | 3 | 已定 | im:message | 0 | D3 |

443	| 群交互卡片 | 3 次点击 | 卡片 JSON + 回调服务 | +卡片回调权限 | ⚠️ **需实测** | 波次 1 之后 |

681	```

756	
757	| 模式 | 机制 | 延迟 | 前置条件 | 自动化次数 |

761	
762	**长连接模式的优势**：
763	- 延迟从"最长一个轮询周期"降到毫秒级 → **即时反馈恢复**，这对学习闭环是关键属性（答完立刻看到"✓ 下次 9月14日"，间隔重复的强化效果才成立）
764	- 不需要反复调 API 拉取 → 无"空轮询"浪费
765	- 回执三态（3.1）的态 1 RECEIVED 天然实时
766	
767	**长连接模式的代价（必须诚实标注）**：
768	```
769	① 需要本地常驻进程
770	   → 机器重启/休眠后进程死掉 → 消息漏收
771	   → 必须配 auto-restart（本仓库已有 auto-restart.ps1，可复用）
772	   → 必须配"进程存活"健康检查，否则又是静默失败
773	② 与现有 GitHub Actions 云端调度的架构不一致
774	   → 云端跑不了长连接（Actions 是短时任务）
775	   → 意味着复习链路彻底本地化，云端只做推送
776	   → 这是一个架构分层决策，不只是技术选型
777	③ 断网期间的消息会在重连后补推，但补推窗口有限
778	   → 需确认飞书的事件重推策略与窗口长度
779	```

784	|---|:---:|:---:|---|---|
785	| **甲：纯轮询** | 60s（建议间隔） | 低 | 轮询进程本身 | 保守稳妥，但即时反馈受损 |

857	### 10.1 🆕 意见 1（P0）：解析器必须与 SDK 同等纳入 hash 自检

874	### 10.2 🆕 意见 2：正则解析的容错边界要写成测试用例表
875	
876	原方案 P1-7 只写了"正则 + 卡片序号映射 + 错例提示"。**没有定义容错到哪一级**。这是解析器最容易失控的地方 —— 太严则用户频繁被打回，太松则误解用户意图（比误判更糟，因为它静默）：
877	
878	| 输入 | 期望解析 | 容错级别 | 备注 |
879	|---|---|:---:|---|
880	| `会 1` | (1, 会) | 标准 | 基准形态 |
881	| `会1` | (1, 会) | ✅ 容错 | 无空格，高频输入习惯 |
882	| `1 会` | (1, 会) | ✅ 容错 | 序号在前 |
883	| `会 一` | (1, 会) | ⚠️ **建议容错但需回执确认** | 中文数字，误判风险中等 |
884	| `会1 不2 会3` | 三组 | ✅ 容错 | 批量（5.2） |
885	| `都会` | ❓ | ❌ **拒绝 + 提示** | 无序号，无法映射到具体卡 |
886	| `会` | ❓ | ❌ **拒绝 + 提示** | 同上；若当日只有 1 张卡可考虑默认，但需明确定义 |
887	| `不会 2` vs `不 2` | (2, 不会) | ⚠️ `不 2` 需确认 | `不` 是 `不会` 前缀，正则贪婪匹配易错 |
888	| `模糊 3` / ` unsure 3` | (3, 模糊) | 只认中文枚举 | 英文一律拒绝 |
889	| `会 99` | ❌ 拒绝 | 序号超出今日队列 | 对应 5.3 的"部分成功"回执 |
890	
891	**这张表本身就是契约测试⑮的测试数据**（建议新增 **⑮ 解析器容错边界：上表 10 类输入各一条断言**）。
892	
893	> **关键取舍**：`都会` / `会`（无序号）**必须拒绝**，即使当日只有 1 张卡。因为"猜对"会强化用户的模糊输入习惯，等到某天有 3 张卡时，同一个 `会` 就会歧义 —— **静默误判的代价延迟爆发，比立刻报错难查得多**。

953	### 11.2 🆕 意见 2（P0 · N17）：每日 3 张的**构成比例**必须定义，否则间隔重复头三周空转
954

956	
957	```
958	第 1 天：到期卡 0 张（没有任何卡有复习历史）→ 补 3 张新卡
959	第 2 天：到期卡 0 张（第1天的3张按间隔表，下次是 1-2 天后）→ 补 3 张新卡
960	第 3 天：到期卡 1-2 张 → 补 1-2 张新卡
961	…
962	前 8 天：23 张存量卡全部引入完毕
963	```
964	
965	**问题不在于"引入太快"，而在于头两三周的学习性质变了**：
966	
967	| 时段 | 构成 | 学习性质 |
968	|---|---|---|
969	| 第 1–8 天 | 以新卡为主（每天 2–3 张全新内容） | **学习新知**，不是复习 |
970	| 第 9–23 天 | 新卡与到期卡混合 | 过渡 |
971	| 第 24 天起 | 到期卡为主 | **真正的间隔重复** |
972	
973	**间隔重复的核心机制是"在遗忘临界点巩固已有记忆"**。头 8 天连续摄入 23 张全新卡片，用户面对的是**密集新知识学习**，而非复习 —— 这既容易过载，也让系统在头三周无法产出任何"记忆保持率"数据（因为没有一条真实的复习流水）。
974	
975	**更要紧的是**：原方案第五章/第十三章都寄望于"第 30 天用真实数据做池化校准"。若头 8 天全是新卡、第 9–23 天才开始有复习流水，**到第 30 天只有约 7–20 天的真实复习数据**，且这 20 天还混着新卡引入的噪声。

977	### 11.3 🔴 待拍板③：新卡引入节奏（三选一）
978	
979	| 方案 | 规则 | 23 张引入完毕 | 头三周性质 | 评价 |
980	|---|---|:---:|---|---|
981	| **甲（原方案隐含）** | 到期卡优先，新卡补足到 3 张 | **约 8 天** | 密集新知学习 | 见效快，但间隔重复机制延迟启动，且池化校准数据被新卡噪声污染 |
982	| **乙（本轮推荐）** | **新卡上限 1 张/日**，其余 2 位强制留给到期卡 | **约 23 天** | 从第 2 天起就有真实复习流水 | ✅ 间隔重复机制立即运转；池化数据纯净；符合"宁可慢、不可假" |
983	| 丙 | 新卡上限 2 张/日 | 约 12 天 | 折中 | 折中但两头不占优 |
984	
985	> **推荐乙的三条理由**：
986	> 1. **学习科学**：间隔重复的效果取决于"复习时机是否恰当"（原方案 12.2 意见 1 自己写过这句话）。每天只引入 1 张新卡，才能保证从第 2 天起每天都有到期卡可复习 —— 让机制**立刻**运转，而不是等 8 天。
987	> 2. **数据质量**：池化校准需要真实的复习流水。乙案从第 2 天就开始积累，到第 30 天有 29 天纯净数据；甲案只有约 22 天且混噪。
988	> 3. **认知负荷**：23 张卡是存量积压，8 天灌完等于每天 3 张全新内容。乙案摊到 23 天，每天 1 新 + 2 复习，是可持续的节奏。
989	>
990	> **代价（诚实标注）**：乙案下用户要 23 天才见完全部存量卡，**前两周会有"怎么老是这几张"的感觉**。需在使用手册写明：

1039	
1040	```
1041	初筛（被否决的方案）的问题：
1042	  · 要一次性对 23 张卡判断"与 60 天冲刺目标是否相关"
1043	  · 判断发生在"还没重新看到卡片内容"的时刻 → 靠回忆做决策，质量低

1056

1058	|---|---|
1059	| SKIP 不计入连续正确次数 | 它不是一次作答 |
1060	| SKIP 不参与跨日门槛 | 不影响升级判定 |
1061	| SKIP 后卡片状态 = ARCHIVED | 不再进队列，但**流水与卡片均不删除** |
1062	| SKIP 可撤销 | 「恢复 5」→ 重新写入一条 `结果=RESTORE`，卡片回到 NOT_STARTED |
1063	| SKIP 可被 `--rebuild-all` 重放 | 幂等 |

1067	### 12.2 🆕 意见 2（P1 · N18）：知识转化 3.91 的真实根因是**只记对错、不记错因**
1068	
1069	原方案把知识转化维度得分最低（3.91，七维度中最低）归因于"检索日志第 1 周末才建，池化校准数据不足"。**这个归因只说对了一半**：
1070	
1071	```
1072	即使检索日志 D1b 就建、数据满 30 天，系统记录的仍然只有：
1073	  card_id / 结果(会|不会|模糊) / 时间戳
1074	
1075	从这些数据能推出：
1076	  ✅ 哪张卡老是答不对（错误率排序）
1077	  ✅ 记忆保持率曲线
1078	  ❌ 【为什么】答不对 —— 而这才是"转化应用"的关键
1079	
1080	"不会"至少有四种完全不同的成因，对应四种完全不同的处置：
1081	  ① 记不清（提取失败）    → 缩短间隔，增加提取练习
1082	  ② 理解错（概念错误）    → 需要重写卡片，光复习没用
1083	  ③ 卡面歧义（题目写得不好）→ 需要改题面
1084	  ④ 知识过期（内容已变）   → 需要更新或归档
1085	```
1086	
1087	**②③④ 三种情况，无论复习多少次都不会变"会"** —— 而系统会一直把它们当"记不清"处理，无限缩短间隔，用户反复挫败。这是知识转化上不去的**结构性原因**，与日志建得早晚无关。

1090	
1091	| 方案 | 指令形态 | 便捷性代价 | 知识转化收益 |

1121	### 12.4 🆕 意见 3：掌握度 M 必须有锚点值，不能留给实现者自由发挥
1122	
1123	原方案 2.2 只说"掌握度只由真实反馈派生"、"INIT 不影响掌握度 M"，**但从未给出 M 的计算公式或锚点**。这意味着 `review_derive.py` 的实现者要自己发明一套 —— 而这套发明**没有任何测试能验证它对不对**（契约测试只能验证"INIT 不污染 M"，不能验证"M 算得合理"）。
1124

1126	
1127	| 场景 | M 期望值 | 说明 |
1128	|---|:---:|---|
1129	| 仅 1 条 INIT，无真实反馈 | **0.00** | 未开始，掌握度为零 |
1130	| 首次答"不会" | **0.00–0.10** | 学过但没掌握 |
1131	| 首次答"会" | **0.30–0.40** | 单次正确不足以证明掌握 |
1132	| 连续 3 次"会"且跨 ≥3 自然日 | **≥0.70** | 达到升级门槛，应显著高于单次 |
1133	| 连续 5 次"会"且最长间隔 ≥7 天 | **≥0.90** | 稳定掌握 |
1134	
1135	**为什么必须给区间而非精确值**：具体公式（指数加权 / 简单计数 / SM-2 变体）可以由实现者选，但**端点行为必须被钉住**。否则会出现"连续答对 5 次，掌握度还是 0.4"这种公式选错却无测试可发现的事故。
1136	
1137	**且 M 必须与升级门槛解耦**：原方案的跨日门槛是**布尔判定**（连续≥3 且跨≥3日 且最长间隔≥3天），不依赖 M 的数值。建议**保持这种解耦** —— M 只用于报表和池化排序，不参与升级判定。这样即使 M 的公式日后调整，也不会影响核心闭环。

1192	### 13.2 🆕 意见 2：ROI 公式的分子不可通约，必须拆开
1193	
1194	原方案 14.2 意见 2 给出：
1195	
1196	```
1197	系统 ROI = 周价值产出（新掌握卡 + 洞察 + 决策）/ 周维护分钟
1198	```
1199	
1200	**这个公式在数学上不成立**：分子是三个不同量纲的东西相加。
1201	
1202	```
1203	"新掌握卡" = 3 张          （单位：张）
1204	"洞察"     = 5 条          （单位：条）
1205	"决策"     = 2 个          （单位：个）
1206	3 + 5 + 2 = 10 ？          ← 10 什么？这个数没有意义
1207	
1208	用它做除法得到的 ROI 更没有意义，
1209	却会因为"是个数字"而被当作趋势指标看待 —— 比没有指标更危险。
1210	```
1211	
1212	**修订建议：拆成三个独立计数 + 一个可通约比值**
1213	
1214	```
1215	周报固定四行（不做加总）：
1216	  新掌握卡（跨过升级门槛）      : N 张
1217	  新增洞察                     : N 条
1218	  新增决策                     : N 个
1219	  本周维护投入                 : N 分钟
1220	
1221	可通约的比值只做一个：
1222	  掌握效率 = 新掌握卡数 / 维护小时数     （单位：张/小时）
1223	  → 分子分母量纲明确，趋势可解读
1224	  → 洞察与决策不进比值，只单独计数看趋势
1225	```
1226	
1227	**为什么这个修订重要**：原方案 14.2 说这个指标"要每周日复盘时看一眼"。**一个无意义的指标被每周看一次，会产生真实的误导** —— 比如某周维护投入下降，ROI 数字上升，看起来系统变高效了，实际可能是新掌握卡也减少了。

1254	  log_type   (单选：RETRIEVAL | INSTRUCTION | ALERT | DEGRADE)

1256	  → INSTRUCTION: 回执三态（态1/态2/态3 + 原始文本 + 解析结果）
1257	  → ALERT      : 告警记录
1258	  → DEGRADE    : L5 顺位切换记录（4.1）
1259	
1260	一张表承载四类只追加日志，表数不变（仍 11 张），且四类日志共用同一套
1261	备份/恢复/TTL 策略 —— 维护成本比四张表低得多。
1262	```
1263	
1264	> 这是本轮**唯一一处做减法的具体动作**：把可能新增的 3 张日志表（指令处理 / 告警 / 降级）压缩为 1 张，且顺带解决了原方案"检索日志表功能单一"的问题。

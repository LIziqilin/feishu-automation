**这不是数字洁癖问题。** 一份要被当作施工图执行的文档，如果它自检声明与实际内容不符，那么施工方对"哪些结论已核验、哪些没有"就失去了判据 —— 这正是历史上"建完就标 ✅，从没验过"的同一病灶，只不过这次发生在文档层而非系统层。

### 2.3 为什么单点估算会系统性偏低

三点估算里 P（悲观值）与 M（最可能值）的比值普遍在 2–3 倍，且悲观情形都不是假想的：

- "查 `im:message` 权限"的 P=30min —— 因为开放平台的权限页需要先确认自建应用归属、可能遇到"权限已申请但未发版生效"的中间态
- "建学习卡 8 字段"的 P=50min —— 字段类型（单选枚举、日期、公式、关联）各有坑，公式字段还可能需要反复试
- "27 任务双跑排查"的 P=40min —— 本地 13 + 云端 14 分处两套系统（任务计划程序 + GitHub Actions），比对需要来回切

**上一版用单点估算，等于默认所有动作都走 M 路径**，这在"第一次做、且要边找入口边操作"的场景下不成立。

### 2.5 附带修订：D1 拆**三**晚而非两晚

上一版拆 D1a/D1b。本轮三点估算显示 D1 预算 216.7min，若拆两晚则每晚 1.8h —— 仍超出"一晚 30–60min"的可执行区间，且第二晚会同时混着"建表"和"写数据/定规则"两类性质不同的工作。


### 3.1 🆕 意见 1（P1 · N14）：文字指令主路径必须建"回执三态"

原方案 1.3 节准确指出按钮路径的历史病是**静默失败**（"自动化超限通常不报错，用户以为点了没用 → 重演 20/23 卡片为空"）。裁决①把主路径换成文字指令后，**这个病没有消失，只是换了载体**：

```
文字指令的静默失败场景（原方案未覆盖）：
  ① 用户打了「会 1」，但轮询周期还没到 → 用户以为没生效，又打一遍
  ② im:message 权限到期/被回收 → 轮询静默读不到消息，用户完全无感
  ③ 解析器不认识「会1」（无空格）或「会 一」（中文数字）→ 消息被丢弃
  ④ 卡片序号 1 在今日队列里已过期（跨日）→ 写入被拒，但用户不知道
```

**四种场景全都不报错，用户侧表现都是"我答了但系统没反应"** —— 与按钮路径的静默失败**完全同构**。

**对策：回执三态可观测**

```
每一条被读到的群消息，必须落到以下三态之一，缺一不可：

  态1 RECEIVED   —— 轮询读到该 message_id
  态2 PARSED     —— 正则解析出 (卡片序号, 结果)
  态3 COMMITTED  —— 已写入流水表且拿到 event_id

告警规则：
  态1 有、态2 无（超过 2 个轮询周期） → 解析失败告警，附原始消息文本
  态2 有、态3 无                     → 写入失败告警，进死信队列
  某日态1 总数 = 0 且用户确有答题     → 权限/轮询失效告警（最高级）

落点：指令处理日志表（可与检索日志表同批建，都是只追加）
```

**为什么这是 AI 工程层的职责**：影子对账保护的是"derive 不静默污染派生值"，回执三态保护的是"用户输入不静默丢失"。两者一前一后，才构成完整链路。**原方案只做了后半段。**

### 3.2 🆕 意见 2（P0 · 影响稳定性）：event_id 用 `message_id`，不要用时间戳

原方案 1.4.3 只写了"两条路径共用同一个 `event_id` 生成规则与幂等表"，**但没定义规则是什么**。第二章给 Seed 定义了 `{card_id}|INIT|{建表时间戳}`，容易被顺势类推成 `{card_id}|{结果}|{时间戳}`。**这个类推是错的**：

```
❌ 若 event_id = {card_id}|{结果}|{时间戳}
   轮询重试 / 补发 / 进程重启后重读同一条消息
   → 时间戳变了 → event_id 变了 → 幂等表拦不住 → 双写重演
   （这正是 V11 obsidian_sync 双注册的机制）

✅ event_id = {message_id}
   飞书每条群消息有全局唯一且稳定的 message_id
   → 无论重读多少次，event_id 恒定 → 天然幂等
   → 幂等表只需一列 UNIQUE 约束即可
```

**按钮路径的对应规则**：按钮回调同样带唯一标识（回调 event_id 或 record_id + 操作时间），**不可用"点击时刻的本地时间戳"**。两条路径各自用平台提供的稳定 ID，才叫"共用同一个生成规则"—— 共用的是**规则形态**（用平台稳定 ID，不用自造时间戳），不是字符串模板。

### 3.3 🆕 意见 3：当日重复作答的语义必须定义

`event_id = message_id` 解决了"同一条消息不被重复写入"，但没解决"用户当天改主意"：

```
09:00 用户打「不会 2」→ 写入 event_A
09:05 用户打「会 2」  → 写入 event_B（不同 message_id，两条都合法）

derive 重算时该取哪条？
```

**建议口径**：**同一自然日内，同一 card_id 取时间戳最后一条为准**（符合"用户改主意"的直觉），但**两条流水都保留不删**（事件溯源只追加原则）。即：流水层全留，派生层取末次。

这条必须写进契约测试（建议新增 **⑭ 当日重复作答，派生结果取末次且流水不被删除**）。

### 4.1 🆕 意见 1（P1）：三顺位之间要有"探测"，不能只有"降级"

| 顺位 | 失效条件 | 探测方式 | 探测成本 |
|---|---|---|---|

| 2° DeepSeek | 余额耗尽 / API 超时 / 限流 | 余额查询 API + 单次调用超时 | 中（联网，且余额查询本身可能计费） |

**对策：探测结果缓存 + 主动健康检查**

```
① 探测结果缓存 5 分钟（避免每次问答都跑三顺位探测，那会让 L5 延迟翻三倍）
② F11 cron（月度保活）扩展为「季度 L5 全顺位演练」—— 与 Coze 季度演练（原 P1-8）合并为同一次执行
③ 顺位切换写日志：何时从 1° 降到 2°、原因是什么、持续多久
   → 这张日志就是"系统实际在用哪个 AI"的唯一真源
```

**为什么重要**：没有探测缓存，L5 每次问答都要串行试三个通道，最坏情况延迟 = 三者超时之和。用户问一个问题等 45 秒，比"直接说不可用"体验更差。

### 4.2 🆕 意见 2：告警线公式补"日均怎么算"

原方案给了 `余额 → 天数 = 余额 / 日均`，三级阈值（<7 黄 / <3 橙 / =0 红）很清楚。但**"日均"的口径没定**，而这直接决定告警是否误报：

```
❌ 日均 = 总消耗 / 使用天数
   → 若系统前 3 天调试期狂跑、后 20 天正常使用，日均被调试期拉高 → 长期误报橙色
❌ 日均 = 昨日消耗
   → 单日波动（比如某天做了一次批量嵌入）就触发降级 → 抖动

✅ 建议：日均 = 最近 7 天的中位数消耗
   → 抗单日尖峰，且比均值更稳健
   → 冷启动期（不足 7 天）用"最近 3 天均值 + 系数 1.5"作保守估计，并标注 COLD_START
```

**这与第二章 Seed 的"冷启动"是同一类问题**：任何基于历史统计的阈值，都必须定义"历史不足时怎么办"。原方案在数据层想到了（Seed），在告警层没想到。

### 4.3 🆕 意见 3（N18 相关）：检索日志要记"没命中"，不只记"命中"

原方案检索日志表的用途是"池化校准"（第 30 天用真实召回数据校准）。但**只记命中，校准会偏**：

```
只记命中 → 能知道"哪些问题被答上了"
         → 不知道"哪些问题问了但没答上"
         → 池化校准时无法识别知识盲区，只能优化已有内容的排序

建议检索日志表增两列：
  hit_count     命中条数（0 表示未命中）
  fallback_level 最终由第几顺位回答（1/2/3/4）
```

**`hit_count = 0` 的记录才是最有价值的**：它直接指出知识库缺什么。这批数据喂给池化阶段一，比命中数据的价值高一个量级。

### 5.1 🆕 意见 1（P0 · 细化阻断项）：`im:message` 不是一个权限，是**三档**

原方案 1.4.1 把 D1a 的动作定义为"查自建应用是否已具备 `im:message` 权限"，结论分"有/无/被拒"三支。**这个二分法在飞书开放平台的实际权限模型下不够用**：

| 档位 | 权限范围 | 用户交互约定 | 审核难度 |
|---|---|---|---|
| **A** | 仅接收 **@机器人** 的群消息 | 用户必须打 `@机器人 会 1` | 低（常见） |
| **B** | 接收群内**全部**消息 | 用户直接打 `会 1`，无需 @ | 高（涉及群隐私，审核严） |
| **C** | 无消息读取权限 | 只能走按钮路径 | — |

**三档对应三份不同的使用手册**，而原方案的分支 A/B/C 是按"有/无/被拒"划分的，**无法区分 A 与 B**。若实际拿到的是 A 档而手册按 B 档写，用户打 `会 1` 不 @ 机器人，系统将完全收不到 —— 且**不报错**，直接落进 3.1 描述的静默失败。

**修订后的 D1a 权限核查（三分支 → 四分支）**

```
查自建应用消息读取权限档位：

  分支 A：拿到 B 档（全量群消息）
    → 手册写"直接打 会 1"，最省事，便捷性最优
  分支 A'：拿到 A 档（仅 @机器人）🆕
    → 手册写"必须 @机器人 会 1"
    → 早报模板需内置 @机器人 的提示文本，降低用户记忆负担
    → 便捷性略降（多一次 @），但仍不占自动化次数
  分支 B：无任何消息读取权限
    → 立即申请，审核期回退按钮路径
  分支 C：申请被拒
    → 永久回退按钮路径 + 题量按次数口径定
```

**这是本轮对可落地性最实质的一处补强**：原方案把"权限"当布尔值，实际它是枚举值，且枚举结果直接决定用户每天要打什么字。

### 5.2 🆕 意见 2（P1 · 便捷性）：**批量文字指令**是比交互卡片便宜得多的改进

原方案 0.2 节诚实标注了裁决①的代价：**便捷性 −0.14**，归因"打字（`会 1`）比点按钮多一步"。第六章把改进希望寄托在"群交互卡片（P1，未来）"上。

**但中间还有一档被跳过了 —— 批量指令**：

```
现状：3 张卡要打 3 条消息
  「会 1」「不会 2」「会 3」     → 3 次输入 + 3 次发送

批量：1 条消息答完 3 张
  「会1 不2 会3」               → 1 次输入 + 1 次发送
  或更宽松：「会 1 3」「不会 2」 → 2 条消息

解析器成本：正则从 r'(会|不会|模糊)\s*(\d+)' 扩展为支持多组
           → 约 15 行代码，无新增权限、无新增表、无新增调度
```

**三档路径的真实成本对照**

| 路径 | 用户动作数 | 开发成本 | 权限依赖 | 自动化次数 | 上线时机 |
|---|:---:|:---:|---|:---:|---|
| 单条文字指令（现状） | 3 | 已定 | im:message | 0 | D3 |
| **批量文字指令（本轮建议）** | **1** | **+15 行正则** | 同上，**无新增** | **0** | **D3 同期** |
| 群交互卡片 | 3 次点击 | 卡片 JSON + 回调服务 | +卡片回调权限 | ⚠️ **需实测** | 波次 1 之后 |

**结论：批量指令用 15 行代码换掉 2/3 的输入动作，且零新增依赖。** 交互卡片反而是三者中成本最高、且引入新的计次不确定性的那个。

> **建议调整优先级**：把"批量文字指令"从隐含状态提升为 **P1 显式项**，排在"群交互卡片"**之前**。交互卡片可以推到波次 2 再评估 —— 因为批量指令落地后，它的边际收益已经不大了。

### 9.1 🆕 意见 1（P1 · N15）：轮询不是唯一选项，**事件订阅长连接**才是

原方案 0.2 节诚实标注了裁决①的代价之一：**效率提升 −0.09，归因"文字指令引入轮询读取"**。N8 也记了"轮询有秒级延迟"。**但原方案默认了"只能用轮询"，从未评估替代通道。**

飞书自建应用接收群消息有两种模式：

| 模式 | 机制 | 延迟 | 前置条件 | 自动化次数 |
|---|---|:---:|---|:---:|
| **轮询**（原方案默认） | 定时调 API 拉取新消息 | 秒级–分钟级（取决于间隔） | 仅 `im:message` 读权限 | 0 |
| **事件订阅·长连接** | 本地常驻进程与飞书建 WebSocket，消息实时下推 | **毫秒级** | `im:message` + 常驻进程 + 事件订阅配置 | 0 |

**长连接模式的优势**：
- 延迟从"最长一个轮询周期"降到毫秒级 → **即时反馈恢复**，这对学习闭环是关键属性（答完立刻看到"✓ 下次 9月14日"，间隔重复的强化效果才成立）
- 不需要反复调 API 拉取 → 无"空轮询"浪费
- 回执三态（3.1）的态 1 RECEIVED 天然实时

**长连接模式的代价（必须诚实标注）**：
```
① 需要本地常驻进程
   → 机器重启/休眠后进程死掉 → 消息漏收
   → 必须配 auto-restart（本仓库已有 auto-restart.ps1，可复用）
   → 必须配"进程存活"健康检查，否则又是静默失败
② 与现有 GitHub Actions 云端调度的架构不一致
   → 云端跑不了长连接（Actions 是短时任务）
   → 意味着复习链路彻底本地化，云端只做推送
   → 这是一个架构分层决策，不只是技术选型
③ 断网期间的消息会在重连后补推，但补推窗口有限
   → 需确认飞书的事件重推策略与窗口长度
```

### 9.2 🔴 待拍板②：事件通道模式（三选一）

| 方案 | 延迟 | 复杂度 | 新增故障点 | 建议 |
|---|:---:|:---:|---|---|
| **甲：纯轮询** | 60s（建议间隔） | 低 | 轮询进程本身 | 保守稳妥，但即时反馈受损 |
| **乙：长连接** | 毫秒级 | 中 | 常驻进程存活 + 断网补推 | 体验最优，但引入"本地必须常开"的约束 |
| **丙：长连接为主 + 轮询兜底** | 毫秒级 | 高 | 两条通道的一致性 | ⚠️ **不建议** —— 两条通道同时读同一批消息，等于在消息层重演双写风险 |

> - 若电脑**长期开机不休眠** → 乙案体验明显更优
> - 若电脑**经常休眠/关机** → 甲案更稳（轮询可在开机后补拉，长连接会漏）

### 10.1 🆕 意见 1（P0）：解析器必须与 SDK 同等纳入 hash 自检

原方案 11.2 意见 2 为 `feishu_sdk.py` 设计了副本漂移防护（`__sdk_hash__` + 调用方启动校验）。**但本轮新增的 `instruction_parser.py` 没有纳入**：

**"宁可当天不记录，也不要记错"** —— 这与超级学习专家的"宁可慢、不可假"是同一原则在软件层的映射。

### 10.2 🆕 意见 2：正则解析的容错边界要写成测试用例表

原方案 P1-7 只写了"正则 + 卡片序号映射 + 错例提示"。**没有定义容错到哪一级**。这是解析器最容易失控的地方 —— 太严则用户频繁被打回，太松则误解用户意图（比误判更糟，因为它静默）：

| 输入 | 期望解析 | 容错级别 | 备注 |
|---|---|:---:|---|
| `会 1` | (1, 会) | 标准 | 基准形态 |
| `会1` | (1, 会) | ✅ 容错 | 无空格，高频输入习惯 |
| `1 会` | (1, 会) | ✅ 容错 | 序号在前 |
| `会 一` | (1, 会) | ⚠️ **建议容错但需回执确认** | 中文数字，误判风险中等 |
| `会1 不2 会3` | 三组 | ✅ 容错 | 批量（5.2） |
| `都会` | ❓ | ❌ **拒绝 + 提示** | 无序号，无法映射到具体卡 |
| `会` | ❓ | ❌ **拒绝 + 提示** | 同上；若当日只有 1 张卡可考虑默认，但需明确定义 |
| `不会 2` vs `不 2` | (2, 不会) | ⚠️ `不 2` 需确认 | `不` 是 `不会` 前缀，正则贪婪匹配易错 |
| `模糊 3` / ` unsure 3` | (3, 模糊) | 只认中文枚举 | 英文一律拒绝 |
| `会 99` | ❌ 拒绝 | 序号超出今日队列 | 对应 5.3 的"部分成功"回执 |

**这张表本身就是契约测试⑮的测试数据**（建议新增 **⑮ 解析器容错边界：上表 10 类输入各一条断言**）。

> **关键取舍**：`都会` / `会`（无序号）**必须拒绝**，即使当日只有 1 张卡。因为"猜对"会强化用户的模糊输入习惯，等到某天有 3 张卡时，同一个 `会` 就会歧义 —— **静默误判的代价延迟爆发，比立刻报错难查得多**。

### 10.3 🆕 意见 3：只追加表的备份要定义"恢复演练"

原方案 11.2 意见 3 指出流水表与检索日志表是不可再生数据，备份优先级最高。**但"有备份"不等于"能恢复"**：

```

  ① 恢复脚本 restore_append_only.py
     --table 流水表 --to-timestamp X → 恢复到 X 时刻的状态
     （事件溯源的优势：只要流水在，任何时点状态都可重建）
  ② 恢复演练（季度，与 Coze 演练同批）
     用备份在【测试表】上跑一次 --rebuild-all，比对派生结果与生产一致
     → 演练的是"备份可用"，不是"备份存在"
  ③ 备份完整性校验
     备份文件写入后立即读回校验条数与哈希，失败则告警
     （历史上"备份脚本静默失败半年"是常见事故）
```

**这三件事的成本约 1h，但它是"事件溯源单一真源"这个设计承诺的最后一道保险。** 原方案把 derive 的三重保险做得很扎实，却没给"流水表本身丢了"这个更根本的故障留出口。

| SKIP 不参与跨日门槛 | 不影响升级判定 |
| SKIP 后卡片状态 = ARCHIVED | 不再进队列，但**流水与卡片均不删除** |

### 12.2 🆕 意见 2（P1 · N18）：知识转化 3.91 的真实根因是**只记对错、不记错因**

原方案把知识转化维度得分最低（3.91，七维度中最低）归因于"检索日志第 1 周末才建，池化校准数据不足"。**这个归因只说对了一半**：

```
即使检索日志 D1b 就建、数据满 30 天，系统记录的仍然只有：
  card_id / 结果(会|不会|模糊) / 时间戳

从这些数据能推出：
  ✅ 哪张卡老是答不对（错误率排序）
  ✅ 记忆保持率曲线
  ❌ 【为什么】答不对 —— 而这才是"转化应用"的关键

"不会"至少有四种完全不同的成因，对应四种完全不同的处置：
  ① 记不清（提取失败）    → 缩短间隔，增加提取练习
  ② 理解错（概念错误）    → 需要重写卡片，光复习没用
  ③ 卡面歧义（题目写得不好）→ 需要改题面
  ④ 知识过期（内容已变）   → 需要更新或归档
```

**②③④ 三种情况，无论复习多少次都不会变"会"** —— 而系统会一直把它们当"记不清"处理，无限缩短间隔，用户反复挫败。这是知识转化上不去的**结构性原因**，与日志建得早晚无关。

### 12.3 🔴 待拍板④：是否启用错因标记

| 方案 | 指令形态 | 便捷性代价 | 知识转化收益 |
|---|---|---|---|
| **甲：不启用**（原方案） | `不会 2` | 无 | 无（保持 3.91 的结构性上限） |
| **乙：可选标记**（本轮推荐） | `不会 2` 或 `不会 2 理解错` | 极低（不填则默认"记不清"） | 错因分布可统计，②③④ 类卡片可被识别并分流 |
| 丙：强制标记 | 必须填错因才能提交 | 高（每次多打 3–4 字） | 数据最全，但摩擦大，用户会敷衍填写 → 数据质量反而下降 |

**乙案的具体设计**：

```
指令扩展（全部可选，不填即用默认值）：
  不会 2 记不清     ← 默认值，可省略
  不会 2 理解错     → 触发"卡片需重写"待办，进周二批处理
  不会 2 题目歧义   → 触发"题面需修改"待办
  不会 2 已过期     → 触发"内容需更新或归档"待办
  模糊 2 记不清     ← 模糊同样支持错因

流水表增列：
  错因 (单选：记不清|理解错|题目歧义|已过期|空)
  → 空值表示"会"或"用户未填"，两者在报表中分开统计

报表增项（周报）：
  · 错因分布饼图（记不清 X% / 理解错 Y% / …）
  · 「理解错」连续 2 次的卡片清单 → 优先级最高的重写候选
```

**为什么推荐乙而非丙**：丙案的强制标记会带来两个反效果 —— ① 摩擦上升导致用户敷衍（一律填"记不清"），数据看似完整实则无效；② 违背本方案一以贯之的"降低复习摩擦"原则。**乙案用默认值把成本压到零，同时保留了获取错因的通道**，符合"可选增强、不设障碍"的设计。

**若采纳乙案，评分影响**：知识转化维度 3.91 → 4.41（本轮矩阵已按乙案计入）。
**若否决乙案**：知识转化仅能到约 **4.20**（靠检索日志提前 + `hit_count=0` 补盲），总均从 4.56 回落至约 **4.53**。

### 12.4 🆕 意见 3：掌握度 M 必须有锚点值，不能留给实现者自由发挥

原方案 2.2 只说"掌握度只由真实反馈派生"、"INIT 不影响掌握度 M"，**但从未给出 M 的计算公式或锚点**。这意味着 `review_derive.py` 的实现者要自己发明一套 —— 而这套发明**没有任何测试能验证它对不对**（契约测试只能验证"INIT 不污染 M"，不能验证"M 算得合理"）。

**建议固定五个锚点，写进契约测试⑯**：

| 场景 | M 期望值 | 说明 |
|---|:---:|---|
| 仅 1 条 INIT，无真实反馈 | **0.00** | 未开始，掌握度为零 |
| 首次答"不会" | **0.00–0.10** | 学过但没掌握 |
| 首次答"会" | **0.30–0.40** | 单次正确不足以证明掌握 |
| 连续 3 次"会"且跨 ≥3 自然日 | **≥0.70** | 达到升级门槛，应显著高于单次 |
| 连续 5 次"会"且最长间隔 ≥7 天 | **≥0.90** | 稳定掌握 |

**为什么必须给区间而非精确值**：具体公式（指数加权 / 简单计数 / SM-2 变体）可以由实现者选，但**端点行为必须被钉住**。否则会出现"连续答对 5 次，掌握度还是 0.4"这种公式选错却无测试可发现的事故。

**且 M 必须与升级门槛解耦**：原方案的跨日门槛是**布尔判定**（连续≥3 且跨≥3日 且最长间隔≥3天），不依赖 M 的数值。建议**保持这种解耦** —— M 只用于报表和池化排序，不参与升级判定。这样即使 M 的公式日后调整，也不会影响核心闭环。

### 13.2 🆕 意见 2：ROI 公式的分子不可通约，必须拆开

原方案 14.2 意见 2 给出：

```
系统 ROI = 周价值产出（新掌握卡 + 洞察 + 决策）/ 周维护分钟
```

**这个公式在数学上不成立**：分子是三个不同量纲的东西相加。

```
"新掌握卡" = 3 张          （单位：张）
"洞察"     = 5 条          （单位：条）
"决策"     = 2 个          （单位：个）
3 + 5 + 2 = 10 ？          ← 10 什么？这个数没有意义

用它做除法得到的 ROI 更没有意义，
却会因为"是个数字"而被当作趋势指标看待 —— 比没有指标更危险。
```

**修订建议：拆成三个独立计数 + 一个可通约比值**

```
周报固定四行（不做加总）：
  新掌握卡（跨过升级门槛）      : N 张
  新增洞察                     : N 条
  新增决策                     : N 个
  本周维护投入                 : N 分钟

可通约的比值只做一个：
  掌握效率 = 新掌握卡数 / 维护小时数     （单位：张/小时）
  → 分子分母量纲明确，趋势可解读
  → 洞察与决策不进比值，只单独计数看趋势
```

**为什么这个修订重要**：原方案 14.2 说这个指标"要每周日复盘时看一眼"。**一个无意义的指标被每周看一次，会产生真实的误导** —— 比如某周维护投入下降，ROI 数字上升，看起来系统变高效了，实际可能是新掌握卡也减少了。

### 13.3 🆕 意见 3：把"减法"从口号变成机制 —— 资产上限

原方案 14.2 意见 3 赞赏题量降级是"约束驱动设计"。**但整个方案里，"做减法"始终靠事后清理（防空虚感条款），没有事前约束。**

历史事实是：任务数从 5 个（`register_tasks.ps1` 注册的量）涨到了原方案所述的 27 个。**没有上限机制，波次 1、波次 2 之后还会继续涨。**

**建议设三条硬上限**：

```
① 调度任务上限：本地 + 云端合计 ≤ 20 个
   现状 27 个 → 波次 0 收敛目标不是"排查双跑"，而是"降到 20 以内"
   超限时新增任务必须先删一个（一进一出）

② 多维表格上限：≤ 11 张（原方案已定 11 张，本轮确认设为硬上限）
   本轮新增的「指令处理日志表」→ 建议合并进检索日志表（同为只追加日志，
   加一列 log_type 区分即可），避免突破 11 张

③ AI 通道上限：≤ 4 个（ALLM / DeepSeek / Coze / 规则直答）
   已在上限，任何新通道必须先退役一个
```

**②的具体建议**：本轮 3.1 提出的"指令处理日志表"**不单独建表**，而是并入检索日志表：

```
检索日志表 → 更名为「系统事件日志表」，增列：
  log_type   (单选：RETRIEVAL | INSTRUCTION | ALERT | DEGRADE)
  → RETRIEVAL  : 原检索日志（hit_count / fallback_level）
  → INSTRUCTION: 回执三态（态1/态2/态3 + 原始文本 + 解析结果）
  → ALERT      : 告警记录
  → DEGRADE    : L5 顺位切换记录（4.1）

一张表承载四类只追加日志，表数不变（仍 11 张），且四类日志共用同一套
备份/恢复/TTL 策略 —— 维护成本比四张表低得多。
```

> 这是本轮**唯一一处做减法的具体动作**：把可能新增的 3 张日志表（指令处理 / 告警 / 降级）压缩为 1 张，且顺带解决了原方案"检索日志表功能单一"的问题。
